## 摘要
大语言模型（LLM）智能体通过可执行框架与环境交互，这些框架控制工具使用与反馈。针对固定策略优化框架会忽略其行为在学习过程中如何变化，而在固定框架下训练策略则使生成训练经验的接口保持不变。这促使我们在策略训练全程自适应调整框架。我们提出 CoHARL，一种基于种群的强化学习框架，协同演化一个共享策略和一组可执行框架。策略从跨种群的 rollout 中学习，提议器利用执行轨迹在训练期间修订框架代码。CoHARL 在 SWE-rebench 上达到 27.6% 的平均解决率，比仅搜索框架的方法提高 6.4 个百分点。在 SWE-bench Verified 和 Terminal-Bench 2.0 上的实验显示，其在软件工程和基于终端的任务上均取得提升。在相同训练预算下，CoHARL 也优于在 RL 前一次性搜索框架，以及将策略更新与对单个活跃框架的修订交替进行的方法。

## Abstract
Large language model (LLM) agents interact with their environments through executable harnesses that govern tool use and feedback. Optimizing a harness for a fixed policy overlooks how its behavior changes during learning, while training a policy under a fixed harness leaves the interface that generates its training experience unchanged. This motivates adapting the harness throughout policy training. We introduce CoHARL, a population-based reinforcement learning framework that co-evolves a shared policy and a population of executable harnesses. The policy learns from rollouts across the population, and a proposer uses its execution traces to revise harness code during training. CoHARL achieves a 27.6% mean resolved rate on SWE-rebench, improving over harness-only search by 6.4 percentage points. Experiments on SWE-bench Verified and Terminal-Bench 2.0 show gains in software engineering and terminal-based tasks. Under matched training budgets, CoHARL also outperforms searching for a harness once before RL and alternating policy updates with revisions to a single active harness.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体在软件工程、终端操作等任务中的表现，同时取决于**模型权重（policy）**与**可执行框架（harness）**——后者负责 prompt 组装、动作解析、工具响应处理与 episode 控制，既决定推理时执行，也决定训练轨迹的采集方式。
- **核心问题**：现有两条优化路线各自割裂：
  - **仅策略 RL**（如 Plain GRPO）：在固定 harness 下更新权重，无法修复 harness 代码本身的缺陷（如动作解析器拒绝合法工具调用、工具输出处理器丢弃反馈）；策略只能“绕过”缺陷，病因仍在。
  - **仅 harness 搜索**（如 Meta-Harness）：在冻结策略下改代码，不能把模型参数更新纳入学习，无法从错误中学习。
- **关键洞察**：两者在训练中**相互耦合**——修复工具处理器会改变策略获得的反馈与训练轨迹；策略变强后，其执行轨迹又会暴露初始模型下不可见的 harness 弱点。因此“RL 前一次性搜索”无法响应后期失败，“冻结策略”也无法利用新接口采集的经验。
- **研究问题**：如何让智能体的策略与执行接口在**整个训练过程中共同自适应**？

## 2. 方法论

### 2.1 核心思想
- **CoHARL**：基于种群的强化学习框架，协同演化**一个共享策略**与**一组可执行 harness**（而非单个活跃 harness）。
- 策略从跨种群 rollout 中学习；一个独立的 **proposer（提议器）模型**读取当前策略的成功/失败执行轨迹，在训练期间修订 harness 代码；被接受的候选在 step 边界加入训练池，由调度器分配后续 rollout。
- 与 WHALE 等“交替式”方法的关键区别：多个 harness **同时保持活跃**，新候选与旧版本**共同贡献训练经验**，而非替换掉后续所有 rollout 的接口。

### 2.2 形式化目标
- 部署目标：`max_{θ,h} J(θ,h) = E_{x~D} E_{τ~Rollout(π_θ,h,x)}[r(τ)]`（式 1）。
- 训练时调度分布目标：`J̄_t(θ) = E_x Σ_{h∈P_t} q_t(h|x,P_t) E_τ[r(τ)]`（式 2）。调度器定义的接口混合决定了训练分布；调度与 harness 代码在每次更新内保持固定。
- 论文明确指出：调度混合与塑形后的替代目标**不保证**与部署目标共享最优解。

### 2.3 训练循环（Algorithm 1）
1. 在每个 step 边界将 Staged 候选 `Admit` 进训练池 `P`。
2. `Schedule(P)` 选出 N 个 harness slot（不要求 N 个不同版本，可只用种子 harness 起步）。
3. 采样 B 个任务，每个任务分配一个 harness，采集 K 条同任务同接口的 rollout 组。
4. 组内中心化计算优势：`Â_{b,i} = R_{b,i} - (1/k_b) Σ_j R_{b,j}`（式 3）——**在同一 task–harness 对内**做中心化，而非跨不同 harness 的轨迹。
5. 采用 GRPO 式裁剪替代目标（式 4），仅**生成 token** 计入 loss，工具观察仅作条件上下文；使用非对称裁剪 `[1-ε⁻, 1+ε⁺]`。
6. 若 batch 准备后可用样本过少，该 step 可**不执行优化器更新**。
7. 周期性触发 harness 搜索，被接受候选 staged，下一 step 才生效（绝不作用于已采集的 batch）。

### 2.4 Harness 搜索机制
- **Proposer 作为随机变异算子**：`h' ~ q_LLM(· | h_par, T_{θ_t}(h_par), F)`，可重写 prompt、parser、tool handlers、甚至 rollout loop。
- 条件输入包括：父代源码、**当前策略**在父代下的成功/失败轨迹摘要 `T`、历史 **Pareto 前沿** `F`、同轮被拒尝试。
- **两条硬约束**：不得修改训练框架；不得改变策略使用的动作格式族。
- **领域相关候选检查**：SWE 为结构 contract 检查 → 训练池 trial；TB-2 额外加 smoke test 与 20 任务候选验证。
- **池调度**：难度调整性能分 + 下置信界保护（式 5）：`g_h = EWMA[(r - b_x) w_x]`，`g_lcb = g_h - c/√max(n_h,1)`；LCB 降低欠采样成员得分，但防过早淘汰靠**强制试验**与最小使用规则。该分数只影响“采集哪些经验”，**不进入**式 3 的训练优势。
- **历史 accuracy–cost archive**：保留非支配的 (accuracy, 生成 token 成本) 记录；archive 中的版本**不能**作为父代（父代须在活跃池中）；archive 提供跨版本历史权衡上下文，分数不随策略更新而重估。

## 4. 主要结果与发现

### 4.1 主实验（SWE-rebench held-out）

- **总体趋势**：CoHARL 在 avg@3 严格 resolved 指标上优于 Plain GRPO 与 Meta-Harness，且优势随训练步数扩大，说明“共同自适应”的收益不是一次性搜索或单侧更新可以替代的。
- **Plain GRPO 的天花板**：固定 harness 下策略提升会饱和，失败模式集中在 harness 层面的解析/反馈缺陷，策略只能学到规避而非修复。
- **Meta-Harness 的天花板**：冻结策略下搜索出的 harness 在早期有效，但无法利用策略变强后暴露的新失败模式；且搜索缺少“策略在环”的反馈信号，候选质量评估依赖旧策略轨迹，存在分布错配。
- **种群的价值**：多个 harness 同时活跃使训练分布覆盖多种接口行为，避免了单一 harness 被过早锁定（对应 2.4 的 LCB 与强制试验设计）。

### 4.2 跨数据集迁移（SWE-bench Verified）

- 零额外适配下，CoHARL 训练得到的策略与 harness 种群仍能迁移，说明学到的不是对特定任务集的过拟合，而是较通用的“接口—策略”协同行为。
- 迁移增益小于同分布评测，符合预期：harness 的部分修改带有任务族特异性（如特定仓库的测试调用约定）。

### 4.3 终端任务（TB-2）

- 在 Terminus-2 基线 harness 上，CoHARL 同样取得提升，表明方法不局限于 SWE 场景；但 TB-2 的配置差异（更多 rollout、更高温度、更长超时）提示超参对结果敏感。
- TB-2 的候选验证更严格（smoke test + 20 任务验证），因此 harness 接受率更低但单次接受的质量更高。

### 4.4 消融与机制分析

- **单 harness 退化**：种群容量为 1 时性能接近交替式方法，验证“多 harness 同时活跃”是核心设计而非实现细节。
- **轨迹条件的作用**：去掉成功/失败轨迹摘要后，proposer 提案的相关性显著下降，接受率与最终性能双降，说明“策略在环”的反馈是搜索有效性的关键。
- **调度器的作用**：去掉 LCB 后欠采样 harness 被过早淘汰，种群多样性下降；去掉强制试验后新候选难以获得足够 rollout 证明自己。
- **奖励消融**：去掉过程奖励与提交门控后，训练信号更稀疏，组过滤（式 3 的非均匀组）频率下降，与命题 1 的直觉一致。
- **成本维度**：archive 的 accuracy–cost 前沿显示，部分高性能 harness 伴随更高生成 token 成本，说明“性能提升”并非无代价，部署时需按预算选点。

### 4.5 安全性 / 完整性发现

- 隐藏测试泄漏审计未发现被接受 harness 访问隐藏测试；但论文明确承认审计是**有限**的，不能形式化保证安全。
- 另一组搜索中全部提案被拒，说明审计门确实在起作用，但也提示 proposer 在约束下的有效提案率可能偏低。

## 5. 贡献总结

1. **问题重构**：把“策略优化”与“harness 工程”从两条割裂路线统一为**联合自适应**问题，并给出部署目标与训练目标的显式区分。
2. **方法贡献**：提出基于种群的 CoHARL，使多个 harness 同时贡献训练经验；将 LLM proposer 形式化为受约束的随机变异算子，并以 Pareto archive 提供跨版本上下文。
3. **训练细节贡献**：明确组内中心化应在**同一 task–harness 对**内进行，避免跨接口轨迹混合导致优势估计偏置；harness 候选只在 step 边界生效，保证 batch 内接口一致。
4. **实证贡献**：在 SWE-rebench、SWE-bench Verified、TB-2 上验证方法有效性与可迁移性，并给出较完整的消融与安全性审计。
5. **理论直觉**：用命题 1 解释“改善接口→提高困难任务上的奖励对比频率”，用命题 2 刻画固定分数 archive 的单调性；作者明确声明二者**不是收敛保证**。

## 6. 局限与批判性评估

- **目标不一致性**：论文自认调度混合与塑形替代目标不保证与部署目标同最优；这意味着训练得到的“平均 harness 策略”在部署时需选定具体 harness，存在选择偏差。
- **算力公平性**：proposer 调用（Claude Opus 4.7）与候选验证（20 任务）成本较高，若不计入对比基线预算，性能比较可能被高估。
- **审计的有限性**：隐藏测试泄漏只能靠代码检查与门控，缺乏形式化隔离；在更长训练或更强 proposer 下风险会上升。
- **理论薄弱**：两个命题均为直觉性刻画，缺少收敛性或样本复杂度保证；命题 1 在 p>1/2 后反转，说明“改接口总是有益”的直觉并不普遍成立。
- **单一策略模型**：仅在 Qwen3.5-35B-A3B + LoRA 上验证，未覆盖全参数训练或更小/更大模型，外推性有限。
- **harness 动作格式约束**：禁止改变动作格式族，虽然保证了解析兼容，但也限制了搜索空间，可能错过更根本的接口重设计。
- **评测温度与采样**：avg@3、温度 0.7 等设置对结论稳健性有影响，论文未充分报告方差或多种子结果。

## 7. 启示

- 对智能体训练而言，**“接口也是可学习对象”**：把 harness 视为策略环境的一部分，而非静态工程产物，能解释并修复仅靠权重更新无法解决的失败。
- 工程上，**step 边界生效 + batch 内接口固定**是保证 RL 正确性的必要约束，任何在线改接口的系统都应遵循。
- 评估上，需同时报告**性能与成本**（token、proposer 调用、验证任务数），否则“协同演化”的收益可能被算力投入掩盖。
- 安全上，**隐藏测试隔离应是硬约束而非审计软约束**，建议采用沙箱级隔离与提案静态分析双保险。
