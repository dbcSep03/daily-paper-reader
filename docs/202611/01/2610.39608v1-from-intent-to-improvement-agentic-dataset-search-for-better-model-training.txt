## Abstract 

Finding training data in million-scale machine learning reposito-ries is a Web search problem where text relevance is not enough. A query couples a semantic training goal with constraints such as task, license, and training stage, and the metadata that would verify them are often missing. Text retrieval ranks dataset cards by similarity but cannot enforce hard constraints or follow the rela-tions that reach a sparsely described dataset. Free-form tool-calling agents are more flexible, but the same model that picks a dataset also declares it a match, and nothing checks that the query’s con-straints are actually met. Neither approach establishes that the data it returns will improve model training. To address it, we propose AgenticDS, a contract-governed agentic framework in which every language model decision instantiates a typed object before deter-ministic code consumes it. The framework compiles a query into a typed search plan, executes it through admissible deterministic operators over hybrid retrieval and bounded graph expansion, and verifies the provenance-grounded evidence before accepting a rank-ing or emitting a typed diagnosis that permits only local repairs. On HuDS-Bench, a new benchmark of 200 queries with 24,908 graded judgments pooled over 15 systems, AgenticDS improves NDCG@10 by 25.7% over the strongest dense–sparse hybrid and by 18.9% over a commercial LLM agent. A controlled search-to-train study fur-ther shows that the datasets it retrieves give the best downstream accuracy in mathematics, code, and medicine. Code and data are publicly available at https://github.com/nju-websoft/AgenticDS.

## 1 Introduction 

Open machine learning (ML) platforms, exemplified by Hugging Face, 1 now host millions of interconnected datasets, models, papers, and curated collections. For a researcher who wants to improve a model, dataset acquisition is already a Web search problem: an underspecified training need must be turned into search opera-tions over inconsistent metadata, relations across heterogeneous resources resolved, and candidates judged by whether they will change the behavior of the model being trained [2–4, 27]. Key-word and embedding-based retrieval help when dataset cards are complete, but they fail on hard structured constraints and ignore evidence implicit in training provenance, task tags, paper citations, or community collections [7, 8, 12, 29, 47]. Natural language dataset acquisition poses three coupled tech-nical challenges . (1) A query mixes a semantic training goal with typed constraints such as task, modality, license, and training stage. Existing dataset search systems either flatten the query into one embedding [9, 46] or treat metadata fields independently [3, 11], so constraint violations stay invisible . Handing the tools to an LLM restores flexibility but adds no verification, so the same model that selects a dataset also declares it a match [22, 45]. (2) Evidence is heterogeneous. Text retrieval is precise when dataset cards are well written [7, 47], while knowledge graph (KG) relations recover resources whose descriptions are sparse [8, 29, 31]. Structural con-nectivity does not imply semantic fit, however, so a naively added 

graph channel can hurt relevance when nothing suppresses the noise it introduces [31]. (3) Retrieval relevance does not entail training utility. Standard benchmarks score ranking against graded rele-vance judgments [10, 30] but never measure whether the selected data improve a downstream model , so linking search quality to data-centric recursive self-improvement (RSI), the loop in which evaluation results drive changes to the training data [49], requires a protocol that measures that change directly. To address these challenges, we present AgenticDS , a contract-governed agentic framework for Web dataset acquisition. A Planner 

compiles the query into a typed search plan of constraints, allowed KG relations, and acceptance criteria. An Engineer executes only admissible deterministic operators over hybrid retrieval, bounded

The contracts stop an LLM from silently redefining retrieval semantics during tool use, while the evidence trace keeps text, metadata, content, and KG support separately inspectable. To evaluate this design, we build HuDS-Bench , a KG-grounded benchmark of 200 natural language dataset search queries with 24,908 graded judgments pooled over 15 systems. AgenticDS out-ranks every system in the pool, and removing the Critic or the Planner costs 0.149 and 0.086 NDCG@10. We then test whether better retrieval translates into better training, feeding each system’s top-5 datasets into corresponding supervised fine-tuning (SFT) of three base models across mathematics, code, and medicine. Agen-ticDS gives the best downstream accuracy in all three domains, with the largest gain on the weakest base model, supporting the view that external acquisition complements within-corpus data-centric RSI. Ablation then isolates where relational evidence pays: graph expansion whose candidates pass straight into the ranking lowers accuracy on every text backbone, whereas the same expansion be-hind a provenance-aware Critic improves it, so expansion coupled to verification rather than the graph itself is the mechanism. In summary, our contributions are threefold: 

• We formulate natural language dataset acquisition on the Web as contract-governed agentic retrieval, and present AgenticDS, whose typed plans, evidence records, and di-agnoses separate semantic reasoning from deterministic ex-ecution. 

• We show that relational evidence is conditional rather than additive, and contribute the per-candidate provenance rep-resentation that lets a verifier turn graph expansion from a liability into a gain. 

• We release HuDS-Bench and a search-to-train protocol that measures whether retrieved datasets improve a model, and use them to compare 15 retrieval systems and to fine-tune three base models across mathematics, code, and medicine. 

## 2 Related Work 2.1 Dataset Search on the Web 

Dataset search differs from document retrieval because relevance depends on structured constraints, data content, and intended use beyond text [4]. Beyond Google Dataset Search’s Web metadata index [3], later work targets dense representations [9, 31], query-focused snippets [7, 12, 47], and integrated public portals [11]. Clos-est to our setting, DataFinder recommends scientific datasets from a natural language description of a research idea [39]. It maps one free-text need to a flat bi-encoder ranking over a fixed corpus, without typed constraints, relational evidence, or any check that the recommended data help training. These are the three axes this paper adds . Benchmarks such as ACORDAR evaluate public-data retrieval [10, 30] but do not model natural language data needs over modern ML hubs. Relational evidence has been explored through general knowledge bases [31] and taxonomies of dataset relation-ships [29]. HuggingKG links datasets with models, tasks, papers, spaces, and collections [8]. These lines supply the primitives and rela-tional infrastructure AgenticDS composes under a typed contract . We adopt the HuggingKG snapshot as auxiliary infrastructure rather than as a contribution of this paper, using it as one candidate source alongside dense and sparse retrieval, and design HuDS-Bench so that natural language data needs become directly measurable .

## 2.2 Agentic Information Retrieval 

LLM agents combine planning, tool use, and reflection [43], build-ing on retrieval-augmented generation [25] and LLM rankers [37]. Zhang et al. [45] formalize “agentic information retrieval” as agents that plan, execute, and refine multi-step search strategies. Search-R1 [22] learns when to call a search engine during reasoning, and Search-o1 [28] embeds agentic Web search into extended reasoning chains. A study of 14 million real queries shows that agentic intents and trajectories differ markedly from traditional Web search [32]. Most such systems target open-domain question answering and give the LLM direct control of tools, which entangles query inter-pretation with index operations and makes errors and reruns hard to compare. Commercial coding agents prompted to search Hug-ging Face behave the same way. AgenticDS instead keeps semantic reasoning inside typed contracts and leaves indexing, traversal, fil-tering, and scoring deterministic , trading open-ended tool flexibility for reproducibility, provenance-transparent ranking, and bounded token cost. 

## 2.3 Data-Centric Recursive Self-Improvement 

Data-centric RSI systems filter, select, rewrite, or synthesize sam-ples from a known corpus. DataEvolver learns preparation pipelines from raw data and seeds through operator- and pipeline-level feedback [17]. DataFoundry evolves a data-construction runtime and synthesizes instruction–response pairs from supplied docu-ments [42]. The broader literature studies evaluation-driven up-dates to data, retrieval state, memory, or policies [13, 40, 44, 49]. 

All presuppose a corpus already in hand and optimize data within it, while our work targets the preceding step . We acquire external datasets from an open Web ecosystem given a user query, and verify utility through controlled fine-tuning. That search-to-train primi-tive is the ingredient these systems assume, positioning AgenticDS as a complementary upstream component of future data-centric loops rather than a competing in-corpus optimizer.

## 4 Evaluation Methodology 

We evaluate two research questions. RQ1 : Can AgenticDS retrieve datasets that satisfy complex natural language training needs on a modern ML hub? RQ2 : Can the retrieved datasets improve models when used as training interventions? RQ1 uses a dataset search benchmark and ranking metrics. RQ2 holds training budgets and optimization settings constant so that differences arise from dataset acquisition rather than training recipe. 

## 4.1 HuDS-Bench 

HuDS-Bench targets realistic Web dataset search over HuggingFace and consists of 200 English queries of four types, two semantic 

(general and fine-tuning) and two relational (paper-reference and entity-neighbor). Its construction is KG-grounded. An extractor derives structured conditions from a gold dataset’s metadata and, for relational types, from HuggingKG [8] anchors. An LLM, GLM-5.2, writes a concise user need from a controlled subset of those conditions, seeing the anchor and target relation but not the gold dataset’s identity or card text for the two relational types. Rule-based checks and manual verification then reject queries that expose the gold dataset’s HuggingFace identifier, copy long card spans, omit intent, or collapse to an exact-name lookup. The four types stress complementary evidence channels (Table 1). The semantic types emphasize semantic goals plus structured con-straints that a dataset card can usually answer. The relational types instead anchor on a paper, model, or collection, and 29 of the 30 entity-neighbor queries are strictly multi-hop. KG relations there-fore enter benchmark construction, so the benchmark can produce needs whose correct answer is unreachable by lexical matching alone. 

## 4.2 Pooling and Relevance Annotation 

Candidate pools merge the top-20 results of all 15 evaluated sys-tems, with the gold dataset injected only when no system retrieves it. The pool holds 24,908 query–candidate pairs. Rather than pass raw dataset cards to an annotator, we compile each query into a structured rubric and assemble a per-candidate evidence package, from which the LLM annotator, DeepSeek-V4-Pro-0813, resolves each constraint to a three-valued status that we deterministically project to a graded 0/1/2 label for the candidate. A second, inde-pendent pass by the same model re-checks every disputed item, and residual disagreements go to human adjudication. Against a 2,490-pair human-annotated sample the pipeline reaches linearly weighted Cohen’s 𝜅 = 0.754, substantial agreement on the conven-tional scale [24]. Appendix C gives the rubric, the label distribution by query type, and the annotation procedure. 

## 4.3 Baselines, Backbone, and Metrics 

We compare AgenticDS against four strong baselines spanning the Web-agent and traditional retrieval families. Two LLM agents 

are implemented with Claude Code and Codex harnesses, both driven by GLM-5.2 [18] and given the same HuggingFace Hub tools. 

Qwen3-Embedding-0.6B + BM25 is a dense–sparse hybrid fused by RRF [16, 46], and monoT5 (OOD) + BM25 is a classic retrieval-then-rerank pipeline [33]. We mark monoT5 (OOD) because it is applied zero-shot, no in-domain training signal existing for this task. Nine further systems span platform search, sparse, dense, and hybrid retrieval . Appendix G lists every system with its configuration and gives the agent tool interface and execution protocol. AgenticDS runs with GLM-5.2 as the agent backbone, Qwen3-Embedding-0.6B as its embedding model, and 𝑇 = 3 iterations unless stated. We also report a second variant that swaps only the embedding model for bge-m3 [5]. Because the same model family generated the HuDS-Bench queries, a shared prior over phrasing could flatter the system. The backbone sweep bounds that concern, since substituting Qwen3.5-35B-A3B from a different family still places AgenticDS above every baseline (Appendix D). All hyperparameters are fixed across reported runs, tuned beforehand on a pilot set disjoint from HuDS-Bench. For RQ1, retrieval quality is measured by NDCG and MAP at cutoffs 5/10/20. Statistical significance is assessed by two-sided paired permutation tests over the 200 per-query scores with Holm correction within each family of comparisons, and confidence in-tervals by paired bootstrap resampling stratified by query type. We fix AgenticDS (Qwen3-Emb) as the reference and correct over the 14 comparisons against the other systems. Appendix E gives the resampling configuration and every test outcome.

## 5.2 Component Ablation 

Figure 2 ablates the AgenticDS search pipeline on HuDS-Bench over ten configurations. This is our primary ablation: it is measured on all 200 queries, every configuration loses accuracy relative to the full system, and the three largest losses all involve the Critic. The Critic and the Planner dominate ( −0.149 and −0.086 NDCG@10), KG expansion follows at −0.084, and the remaining three compo-nents fall between −0.017 and −0.036. The feedback-loop entry removes replanning entirely, stopping after the first round, so its 

−0.036 measures what the whole revision mechanism buys. The adaptive budget is the Engineer’s per-branch allocation of the an-chor, neighbor, and pool budgets, replaced here by an equal split, and sample evidence is the sample fields in the Critic’s evidence package, withheld here. Verification is therefore the load-bearing component, since every configuration that removes the Critic, alone or in combination, falls below both agent baselines. 

One combination is not additive. Removing the Planner and the Critic ( −0.121) is less damaging than removing the Critic alone (−0.149), because without a Planner the Engineer falls back to a wide default retrieval that leaves the unverified ranking more us-able candidates. Without the Critic, KG candidates introduce noise and degrade sparse, dense, and hybrid retrieval alike (Appendix D), confirming that relational expansion requires semantic verification. 

The components therefore interact rather than contribute indepen-dently, so the loop has to be read as a whole even though the Critic carries by far the largest single effect.

## 5.4 Downstream Component Ablation 

Does the search-end ablation survive fine-tuning? Table 4 repeats each single-module ablation through the search-to-train protocol, aggregated over all nine (domain, base model) blocks. It does not resolve the question for any individual component. The per-block changes are dispersed enough that a nine-block mean carries a standard error of 0.6–1.4 accuracy points, so a component would have to move that mean by roughly two points to be separated, and the largest effect, removing the Critic at −1.85, falls just under the bar. We therefore read no per-component downstream attribution out of this experiment in either direction. In particular, the small positive means for KG expansion and the adaptive budget are not evidence against those modules. What the experiment does support is a sign check. Three of the five components move both ends in the same direction, and the largest search-end effect is also the most negative downstream. The exception is informative. Sample evidence is the smallest search-end effect ( −0.017) and the second largest downstream one ( −1.43), consistent with sample snippets mattering for whether a corpus trains well rather than for whether it ranks well. Appendix F.4 gives the per-block grid and discusses why a module can be clearly effective at the search stage and invisible after fine-tuning. The protocol is therefore the right instrument for ranking acquisition methods and the wrong one for assigning credit inside a pipeline, which is why we report its standard error beside its means and keep component attribution at the search end. 

## 5.5 Cost Analysis 

Figure 3 compares AgenticDS with the two agent baselines over the 200 queries, with AgenticDS running under its full 𝑇 = 3 cap. AgenticDS matches Claude Code’s wall-clock time (150.5 vs. 139.3 seconds per query) while billing 12.3M tokens against 111.4M and 280.9M. Most of that token gap is cached prompt reuse billed at a lower rate, so AgenticDS’s relative cost savings are smaller than its relative token savings. Because all three systems run the same GLM-5.2 backbone, one price list settles the comparison: the 200-query evaluation costs $19.86 for AgenticDS against $48.78 and $112.40, savings of 59% and 82%, and AgenticDS is 5 .8× faster than Codex end to end. The saving is a lower bound, since AgenticDS has no cache-hit breakdown and is billed entirely at the uncached input rate. The architectural reason is that the Engineer reads each dataset card at most once and the Critic receives a fixed-format evidence package, whereas free-form tool-calling agents re-fetch and re-read cards during open-ended exploration. Within AgenticDS the two costs sit in different places. The Critic accounts for 83.0% of the tokens but only 28% of the wall clock, the two Planner calls take half the wall clock on 13% of the tokens, and the retrieval and fusion stage is deterministic and spends no tokens at all. Appendix G gives the token totals, the per-system costs, and the price list behind these figures. Bounded autonomy therefore has a measurable payoff. Even with three rounds available, fixing the operator vocabulary and capping the budget holds cost near-constant per query, whereas an open-ended agent’s cost grows with however long it chooses to explore. 

## 6 Discussion 

From retrieval to acquisition. AgenticDS makes dataset search behave more like product search or paper discovery. It interprets a natural language intent, orchestrates structured and unstructured evidence, and returns candidates that serve the operational purpose of training rather than merely matching a description. Applying the separation between interpretation, execution, and verification that is familiar across Web information systems to ML data acquisition buys a guarantee unconstrained tool-calling agents cannot offer, namely that the same plan reaches the same corpus and yields the same candidate set. 

The role of KG evidence. HuggingKG is infrastructure rather than a contribution, and it does two jobs. During search, bounded paths supplement lexical retrieval and record why a resource was reached. During benchmark construction, relation-grounded queries create needs that copying card text cannot meet. The boundary condition on the first job is sharp. Graph candidates added without semantic verification lower NDCG@10 by 0.025–0.029 across three backbones, so expansion and verification are not separable features. Where the graph does pay, it pays as designed: entity-neighbor queries needing one- or two-hop traversal gain +0.197 NDCG@10, against +0.075 for general queries already answerable from card text. Appendix H traces both behaviours on individual queries, including one the system correctly reports as unsatisfiable. 87 Conclusion 

In this paper we presented AgenticDS, a contract-governed agentic framework for natural language instructed dataset acquisition on the Web, in which a Planner, an Engineer, and a Critic exchange typed plans, evidence records, and diagnoses so that semantic rea-soning never silently rewrites what the retrieval stack does. Ex-periments on HuDS-Bench, a new benchmark of 200 queries and 24,908 graded judgments pooled over 15 systems, show consistent improvements over both commercial LLM agents and strong dense– sparse retrieval pipelines, and a controlled search-to-train study confirms that the datasets AgenticDS returns yield the best down-stream accuracy in all three domains we study. Further analysis shows that relational evidence is conditional rather than additive, since graph expansion pays off only once a provenance-aware veri-fier checks the path behind each candidate. Dataset acquisition can therefore be treated as an upstream stage of a data-centric improve-ment loop whose quality is judged by the model it trains rather than by relevance alone. Two limitations bound these claims, since benchmark construc-tion shares a graph with the retrieval engine and the utility study is narrow in coverage. Future work addresses both with a KG-free gold-label pipeline and a distilled Critic. Appendix I gives the de-tails.

## B Contracts, Parameters, and Prompts 

Contracts specify retrieval hypotheses and query-linked constraints and restrict Engineer execution to admissible operators, declared paths, and configurable query, anchor, neighbor, and pool budgets. Search uses a configurable iteration limit, set to 𝑇 = 3 unless stated otherwise, with scoring coefficients and acceptance thresholds fixed across rounds. With preferences, pre-ranking mixes grouped re-trieval support and utility through 𝛽 and 1 − 𝛽 . The final score combines semantic judgment and pre-ranking with weights 𝑤 llm 

and 1 − 𝑤 llm . Missing constraint fields remain unknown, and candi-dates with explicit hard-constraint violations are discarded. Com-pressed metadata, content, and paths support independent Critic scoring. Acceptance tests configured quality and single-candidate joint-intent targets, at least 𝐾 candidates, and absence of criti-cal diagnoses. Feedback permits bounded local plan repair tied to the original query. Search retains the best historical round using quality–coverage utility, with configurable weight 𝜆 . ## C HuDS-Bench Construction Details 

The construction pipeline derives structured conditions (task, modal-ity, language, scale, format) from each gold dataset’s textual meta-data and KG neighborhood, generates a need-centric query, and verifies that the result does not leak the repository identifier or collapse to a single lookup. Candidate pools merge the top-20 re-sults of all 15 evaluated systems. Each candidate’s evidence package contains concise card excerpts, normalized metadata, sample fields and instruction–response snippets when available, and retrieval and graph provenance. Using a structured rubric (released with the code), the LLM annotator marks every constraint satisfied ,

violated , or unknown and cites an evidence code for each satisfied 

or violated decision, which we deterministically project to a graded label. Label 2 requires an exact or strong intent match with satisfied hard constraints, a matched dataset role, and direct evidence, label 1 covers partial matches, and label 0 marks hard conflicts or role mismatches. A verifier model re-checks any item with an evidence conflict, a role mismatch, an unknown on a hard constraint, or an unresolved relation, and disputes are escalated to human review. Table 6 gives the distribution. 

Human agreement study. ## D Extended Retrieval Results 

The complete 15-system comparison is reported in the main text (Table 2). This appendix reports per-query-type retrieval gains, the agent-backbone sweep, and the Critic-free graph experiment. Table 7 lists the per-type gains summarized in Section 5. The two semantic types, which together account for 130 of the 200 queries, gain least. The two relational types, whose gold answers are reachable only through the graph, gain twice as much. The four gains weight-average to the +0.126 overall margin of Table 2. Because the relational types carry a near-binary label distribution (Table 6) and rest on only 40 and 30 queries, their margins are more volatile than the semantic types’, so we read the split between the two families rather than the gap between the relational rows. Table 8 also bounds the architecture’s claim. It varies only the agent backbone, holding the retrieval stack and all contracts fixed. The contracts constrain what the Planner and Critic may emit, not how well they reason: with Qwen3.5-35B-A3B the system still clears every retrieval baseline (0.5244 NDCG@10), but with GLM-4-9B it falls to 0.4706, level with BM25 (0.4717) and below the hybrid baseline (0.4893). The contract-governed loop therefore converts backbone capability into ranking quality without substituting for it, and a frontier-scale Critic is a prerequisite, not an optimization.

## H Case Studies 

Two cases show how contracts organize evidence. (1) For the fine-tuning query “ instruction tuning data with code commit messages as natural language instructions across programming languages ”, the Planner separates code generation, supervision format, and commit provenance into complementary hypotheses. The Engineer’s dense branch returns four commit-oriented corpora in the top-10, two of which the Critic rejects because their sample fields show synthetic rather than real-commit prompts, and those rejections guide a local repair hypothesis. (2) For the general query “ large Hungarian-only medical consultation data ”, none of the top five results is relevant. The Critic diagnoses unmet language and domain requirements, and local repair must preserve the Hungarian-only constraint, which broader Finno-Ugric or English candidates cannot satisfy. Report-ing an unresolvable constraint is the correct behavior here, and 12 separates AgenticDS from both commercial agent baselines, which silently returned near-miss English or Spanish corpora. 

## I Limitations and Future Work 

Limitations. (1) The two relational query types are built from Hug-gingKG anchors that the Engineer can also traverse. The design bounds what that overlap can buy: 130 of the 200 queries carry no KG-derived gold label, every non-KG baseline is given Hug-gingFace’s full-text search, and the variant without KG expansion still reaches 0.5307 NDCG@10, above every non-agent baseline. Extending construction to KG-free gold labels would remove the overlap entirely. (2) With one query per domain across three base models, the utility study is powered to separate acquisition methods in aggregate rather than individual components. Its scope is English queries on a single ML hub, at a latency suited to offline acquisition rather than interactive search. (3) The agreement study reports a single 𝜅 over all four query types. Because the relational types rarely use the middle grade, that figure speaks mainly for the semantic types, and per-type coefficients would be more informative. 

Future work. Four directions follow. Sharpening the search-to-train protocol calls for more queries per domain and repeated seeds rather than more benchmarks. A gold-label pipeline that never consults the graph would settle the overlap above. Distilling the Critic into a smaller pairwise scorer attacks the dominant cost. Finally, only the Engineer is tied to a hub, so any ecosystem with typed metadata and a navigable relation graph could be served by swapping it. A federation layer routing typed constraints to several hubs would test the contracts outside HuggingFace. 13
