Abstract 

As executable environments for language agents scale, generating and verifying their rollouts becomes increasingly expensive. Under finite rollout budgets, this raises an important question: can data management at the environment level make agentic reinforcement learning (RL) more efficient by organizing, evaluating, and scheduling task instances together with the environments that determine their tools, states, transitions, and verification? To address this question, we introduce EnvSched (Env ironment-aware Sched uling), an online scheduler that learns from rollout history. EnvSched assigns scheduling value through two complementary modeling choices: exploitation prioritizes tasks likely to provide informative reward differences, while coverage spreads each batch across underobserved environments and interaction patterns. EnvSched organizes environment–task pairs as nodes in a dual-relation graph, with within-environment edges capturing task semantics and shared tool, state, and verifier structure, and cross-environment edges capturing abstract execution and reward topology. By propagating historical rollout statistics along both edge types, it predicts within-task reward variance. These predictions guide a scheduler that allocates each batch to tasks with high predicted reward variance and underobserved environments and tasks. Environment quotas and a similarity penalty further limit concentration and redundancy, yielding informative and diverse batches without additional pilot rollouts. In RL on Qwen3-8B, 

EnvSched achieves an average score of 48.81 across BFCL-v3, τ -Bench, and ACEBench-Agent after 40 training steps, exceeding the highest score attained by random task selection after 120 steps. It also improves downstream performance across model sizes at the same training budget. Statistical analyses and ablation studies highlight the complementary roles of within-task reward differentiation and cross-environment coverage in these improvements.

1 Introduction 

Large language models (LLMs) are increasingly trained to act in stateful tool environments, where completing a user request requires multi-turn interaction, coordinated tool use, and consistent updates to the underlying state [1–3]. For example, an agent rescheduling a reservation must retrieve the relevant records, check availability and domain rules, and update dependent entries in a valid order. Executable environments support this interaction through database-backed states, tool interfaces, transition logic, and task-specific verifiers. Recent systems have made executable environments a central scaling axis for Agentic RL, expanding training pools from tens to thousands of environments [4–7]. This expansion comes with substantial training costs: industrial reports describe RL over thousands of environments and post-training runs consuming hundreds of thousands of GPU-hours [8–11]. Figure 1 (left) summarizes the growing scale of environments and reported RL resources. As the number of executable environments grows, the cost of generating and verifying RL rollouts grows with them. Researchers [12, 13] and industrial technical reports [10, 11] increasingly emphasize that training efficiency must be improved through better organization of the training data itself, including environment design, trajectory generation, rollout scaling, and curriculum learning. Data-centric systems such as LLM-based subpopulation analysis and unified data workflow automation further illustrate the value of structuring and auditing data before model training [14, 15]. Existing work has begun to study online task selection during RL, estimating training value from task difficulty, prompt representations, or historical rewards [16–18]. However, these methods model the prompt or task while leaving the executable environment outside the selection model. This misses a key source of variation in Agentic RL: the environment determines the tools, initial state, transition rules, and verifier, and thus shapes how a task unfolds and what learning signal it produces. This motivates our formulation of environment-level data management. We formulate this challenge as environment-level data management: organizing, evaluating, and scheduling task instances together with the executable environments in which they are carried out. Each environment specifies the available tools, initial and intermediate states, transition rules, and task verifier. To address this challenge, we draw on the update mechanism of group-relative RL methods such as GRPO [19]. In these methods, reward differences among rollouts of the same task determine their relative advantages; tasks with nearly identical outcomes therefore provide little learning signal. The scheduler should prioritize tasks whose current reward distributions are likely to 

2yield informative differences. At the same time, repeatedly training on a small set of environments restricts the tools, states, transitions, and verification patterns seen by the policy, even when the selected tasks are individually informative. Effective scheduling must therefore preserve diversity across environments and interaction patterns. Building on these two requirements, we introduce 

EnvSched (Env ironment-aware Sched uling), an online scheduler learning from rollout history. It prioritizes task instances with high predicted reward informativeness, while it also spreads each batch across underobserved environments and structurally distinct interactions. 

EnvSched implements exploitation and coverage as two coordinated parts of the same scheduling procedure. To support both decisions, EnvSched represents environment–task pairs as nodes in a dual-relation graph. Within-environment edges connect tasks through shared semantics, tools, database fields, and verifier constraints. Cross-environment edges connect tasks through abstract execution and reward topology, enabling information transfer across similar environments. For example, reassigning a consultant and moving a patient between hospital beds can share a dependency structure of entity lookup, eligibility checking, relation replacement, and dependent-state validation. At each training step, EnvSched aggregates historical rollout statistics separately along the two edge types and combines the resulting estimates to predict each task’s reward variance under the evolving policy. It then allocates half of each batch to underobserved environments and tasks for coverage, and half to tasks with high predicted reward variance for exploitation. Environment quotas and a similarity penalty limit concentration and redundancy within the shared batch, while newly collected rollout outcomes update the node histories for subsequent rounds. This rollout–update– propagation–selection loop balances policy-dependent task prioritization with explicit environment coverage without additional pilot rollouts. We evaluate EnvSched by conducting reinforcement learning on the EnvScaler training pool with matched per-step rollout budgets. The right side of Figure 1 shows that EnvSched reaches an average score of 48.81 on Qwen3-8B across BFCL-v3, τ -Bench, and ACEBench-Agent [20–22] after 40 steps, exceeding the highest score attained by random task selection during 120 steps. It also improves downstream performance at the same training budget, with gains across model sizes. Analysis of selected-task rollouts shows that mean within-task reward variance rises from 0.03208 to 0.04290, and environments covered per batch also rises from 36.53 to 45.96 on Qwen3-4B. Ablation studies confirm that reward differentiation and environment coverage are complementary: either component alone is insufficient for effective training. More broadly, EnvSched demonstrates the distinctive value to efficient Agentic RL training, paving the way for scaling increasingly capable agent models with better use of training budgets. Our contributions are threefold: • We are the first to formulate environment-level data management for Agentic RL, jointly modeling task specifications and executable environment structure. • We propose EnvSched , an Agentic RL training data scheduler which combines a dual-relation graph, historical reward-variance prediction, and coverage-aware batch construction to schedule training tasks without additional pilot rollouts. • We demonstrate consistent gains in rollout efficiency across models of varying sizes and improved performance on a range of downstream tool-use benchmarks. Our analyses show that reward differentiation and environment coverage are complementary sources of training value, establishing environment-level data management as a promising data-centric direction for scaling efficient Agentic RL.

2 Method 

2.1 Problem Setup and Training Loop 

EnvSched treats an environment–task pair as the basic unit of training and scheduling. An environ-ment is an executable setting that defines the tool interfaces, transition rules, state representation, and verifier; a task instance specifies the request and its initial state within that environment. Each pair therefore identifies one concrete rollout problem, and the model interacts with it through text responses and tool calls to produce a trajectory and its task-specific evaluation reward. At each training step, the scheduler chooses a batch of distinct pairs for rollout and model update. As illustrated in Figure 2, EnvSched builds a dual-relation graph from task specifications and executable environment structure before training, then initializes the schedule with a coverage-oriented batch. Rollouts on the selected pairs produce rewards for model updates and statistics for the corresponding node histories. Before the next training step, historical statistics propagate along within-environment and cross-environment edges to estimate task informativeness. The scheduler combines coverage of underobserved environments and tasks with exploitation of informative tasks, using environment quotas and a similarity penalty to limit concentration and redundancy. This rollout–update–propagation–selection loop repeats throughout training. 

2.2 dual-relation graph 

We define G = ( V, Ein , Ecross ) over the environment–task pairs. Each node stores the pair’s historical reward statistics and selection count. The two edge types are constructed from similarity: within-environment similarities compare task semantics and concrete tool, state, and verifier features among pairs in the same environment; cross-environment similarities compare abstract execution and reward structure among pairs in different environments. Similarity determines which observed nodes contribute evidence and how strongly they contribute to the target node’s estimate. Before training, a language model reads the task instruction, initial-state summary, tool descriptions, and verifier to extract a structured operation description. It records required operations, prerequisites, execution dependencies, and relationships between operations and reward checks. For within-environment similarity, six TF–IDF views encode instruction words and character fragments, verifier-check text, verifier code structure, initial context, and the complete operation description. 2.4 Coverage-Aware Task Scheduling 

The scheduler assigns a fraction ρ of each batch to coverage and the remaining fraction 1 − ρ to exploitation. Coverage first restricts the candidate set using a lexicographic priority over current-batch environment coverage, cumulative environment exposure, and task observation count. Within the resulting candidate set, it prioritizes predicted informativeness. Exploitation prioritizes predicted informativeness while gradually discounting repeated exposure. 3 Experiments 

3.1 Experimental Setup 

Training Environments and Evaluation. We train Qwen3-Thinking [23] models with GRPO [19] on the EnvScaler [5] executable-environment pool, which contains 2,550 task instances across 51 executable environments. Each task instance is evaluated through its environment-specific tools, initial state, and terminal verifier. We report performance on BFCL-v3 Multi-Turn, τ -Bench, and ACEBench-Agent [20–22], covering function calling, multi-turn interaction, and long-horizon tool use. 

Implementation Details. For training with EnvSched , we apply a unified GRPO configuration across Qwen3-1.7B, Qwen3-4B, Qwen3-8B, and Qwen3-30B-A3B. Each training batch contains B = 64 

environment–task pairs with rollout K = 8 per pair (512 trajectories). The scheduler uses a fixed coverage fraction ρ = 1 /2, yielding 32 coverage pairs and 32 exploitation pairs. We train for 200 single-epoch steps using Adam (lr = 10 −6, cosine schedule, 10 warmup steps) with a policy-ratio clip of 0.2 and batch-whitened, [−0.2, 0.2] -clipped advantages. Rollouts sample at temperature 0.99 (top-p = 0 .99 , top-k = 100 ) with limits of 40 turns, 4,096 tokens per turn, and 32,000 tokens per sequence. The policy loss covers only model-generated tokens, including reasoning; all other tokens are masked. All scheduler and optimization hyperparameters are fixed across model sizes. 8Consistent gains across model sizes at 200 steps. At the 200-step budget, EnvSched improves over random scheduling for all three benchmark overall scores at every model size. Qwen3-4B illustrates the pattern clearly: BFCL-v3 rises from 28.83 to 31.88 (+3.05), τ -Bench from 37.78 to 41.01 (+3.23), and ACEBench-Agent from 56.00 to 58.00 (+2.00). The gains also hold for the other dense models: at 1.7B, the improvements are +1.96, +2.02, and +2.66, while at 8B they are +4.00, +3.03, and +3.34 on BFCL-v3, τ -Bench, and ACEBench-Agent, respectively. The BFCL gain at 4B is distributed across all four categories, including Base (36.67 to 40.67), Miss-Function (26.17 to 28.17), Miss-Parameter (25.50 to 27.50), and Long-Context (27.00 to 31.17). The gains extend to Qwen3-30B-A3B under the same configuration: BFCL-v3, τ -Bench, and ACEBench-Agent reach 37.79, 54.75, and 70.67, improving over random scheduling by 3.92, 3.03, and 2.67 points, respectively, without model-specific scheduler tuning.  

> High efficiency.

EnvSched is already effective after 40 steps within the 200-step training budget. At 4B, it reaches 30.17 on BFCL-v3, 41.01 on τ -Bench, and 58.00 on ACEBench-Agent, matching its 200-step ACEBench-Agent score. At 8B, the 40-step τ -Bench score reaches 50.71, above the 200-step score of 50.30; at 1.7B, ACEBench-Agent reaches 30.67 versus 31.33 after 200 steps. On Qwen3-30B-A3B, the 40-step scores of 35.00, 53.54, and 70.00 exceed the 200-step random baseline on all three benchmarks. These results show that EnvSched can extract useful training signal quickly and, on some benchmarks, match or exceed its longer-run performance.  

> Prompt-only schedulers do not transfer reliably.

DPS and LEEPS are designed around the informativeness of individual prompts, without modeling the environment coupled to each task. Here, choosing a prompt also chooses the tools, state, and constraints exposed to the policy, so prompt-level selection alone cannot reliably identify useful training data. Both methods underperform EnvSched 

overall, and some of their dimensions are no better than random: DPS is below random on 4B 

τ -Bench (36.77 vs. 37.78), and LEEPS on 8B ACEBench-Agent (54.67 vs. 55.33). The comparison supports combining reward differentiation with environment-aware coverage.   

> 3.3 Analysis
> 3.3.1 Reward Variance and Environment Coverage

On Qwen3-4B, EnvSched improves both reward differentiation and coverage under the same 64-task batch budget (Table 2). Compared with random scheduling, it increases mean within-task reward variance from 0.03208 to 0.04290 (+34%) and median variance by 44%, while median reward remains nearly unchanged. Environment coverage rises from 36.53 to 45.96 per batch (+26%) and tool coverage from 413.41 to 478.39 (+16%), alongside a BFCL-v3 improvement from 28.83 to 31.88. The log-transformed curves in Figure 4 show higher variance and coverage for most of the 200 training steps. Over training, variance declines, but the relative magnitude relationships are preserved, while coverage stays stable, preserving reward differentiation and environment diversity.  

> 3.3.2 Computational Cost

EnvSched reuses historical training outcomes and requires zero additional probe trajectories. For fixed ∆t, ˆK,and B, and without boundary-tie fallback scans, this cost is linear in N . In the measured 200-step run, online selection takes 6,985.94 seconds in total, or 34.93 seconds per step. 3.4 Ablation Studies 

3.4.1 Component Contributions 

We isolate the contributions of the two graph relations and the coverage–exploitation allocation. The relation ablations retain only within-environment edges or only cross-environment edges. The allocation ablations assign all 64 slots to coverage or all 64 slots to exploitation. Table 3 reports performance and statistics. The results show that reward differentiation and environment coverage must be optimized together. Coverage-only scheduling reaches the broadest batches (51.00 environ-ments) but lowers mean reward variance to 0.0357 and degrades all three downstream scores, while exploitation-only scheduling produces the highest variance (0.0442) yet covers only 33.95 environ-ments and performs substantially worse. Combining the two objectives recovers both informative reward differences and broad exposure. Full EnvSched has the highest BFCL-v3 score among the component configurations and ties the within-environment-only variant on ACEBench-Agent. The cross-environment-only variant matches the full model on τ -Bench but performs worse on BFCL-v3 and ACEBench-Agent. Both edge ablations also reduce mean reward variance relative to the full graph. Modeling both relations therefore provides effective transfer of rollout evidence across tasks and environments; qualitative examples appear in Appendix F.

4 Conclusion 

We presented EnvSched , an environment-aware scheduler for reinforcement learning with executable agent environments. By treating environment–task pairs as the unit of data management, EnvSched 

selects tasks with informative reward differentiation while maintaining broad environment coverage. Across Qwen3-1.7B, Qwen3-4B, Qwen3-8B, and Qwen3-30B-A3B, it consistently improves perfor-mance over random scheduling on BFCL-v3, τ -Bench, and ACEBench-Agent under matched rollout budgets, with gains arising from the complementary effects of reward variance and environment diversity. More broadly, this work first establishes environment-level data management as a useful data-centric perspective for efficient agentic RL, paving the way for scaling increasingly capable agent models with better use of training rollout budgets.

> A.1 Executable Environments for Agent Training

Tool-use benchmarks provide executable settings for evaluating agents across function calling and multi-turn interaction. BFCL, τ -Bench, and ACEBench assess complementary aspects of tool invo-cation, user interaction, and task completion [20–22]. Recent environment-synthesis systems extend such interaction to diverse training domains. EnvFactory introduces 85 executable environments with 953 task instances for tool-using agents [4]. EnvScaler [5] programmatically constructs environ-ment skeletons, initial states, task scenarios, and terminal-state validation functions, producing 191 environments and approximately 7,000 scenarios. Agent World Model [6] scales to 1,000 code-driven, database-backed environments with MCP tool interfaces and code-augmented reward verification. Agent-World [7] combines environment–task discovery with multi-environment RL and a self-evolving arena that diagnoses capability gaps and synthesizes targeted tasks. Related work also studies embodied interaction and broad evaluation suites, including world-model interaction, embodied-agent benchmarking, and generative fluid-intelligence evaluation [26–28]. These systems expand the supply of executable environments and verifiable tasks for agent training. EnvSched addresses their use during training by organizing environment–task relationships and selecting informative, diverse tasks from the available pool.  

> A.2 Task Informativeness Estimation and Online Selection

Online task selection adapts the training distribution to the evolving policy by estimating task informativeness from reward variation, historical feedback, and task relationships. Recent technical reports on Agentic RL also treat asynchronous rollout, multi-task mixing, and environment scaling as central data-scheduling problems [10, 11]. In group-relative RL, rollout reward differences identify informative tasks [19]; DAPO [29] filters uniformly successful or unsuccessful groups and resamples prompts, while Pilot-Commit [30] uses reward variation in a pilot sample to allocate later rollouts. For binary rewards, this informativeness is captured by variance p(1 − p). DOTS [16] selects moderately difficult prompts using reference rollouts and an attention-based difficulty predictor, and Dynamics-Predictive Sampling (DPS) [17] models prompt-solving dynamics from historical rollout outcomes to prioritize informative prompts before rollout generation. LEEPS [18] combines representation-space neighbors, historical outcomes, and explore–exploit portfolios to identify prompts likely to yield nonzero reward variance without extra rollouts, while graph-structured online difficulty estimation [31] propagates feedback over semantic and reasoning similarities through coupled latent difficulty states and a state-level Beta–Binomial model. Stable post-training recipes and controllable synthetic-data frameworks provide complementary evidence that data composition and training procedure jointly shape downstream capability [32, 33]. Building on these foundations, EnvSched incorporates executable environment structure through a dual-relation graph: within-environment edges capture shared tools, database fields, and verifier constraints, while cross-environment edges capture abstract execution and reward topology. These predictions guide task selection with explicit environment coverage, modeling both individual task informativeness and batch-level interaction patterns.

C Scheduling Rules and Cold Start 

The coverage phase first restricts the eligible candidates lexicographically by current-step coverage count, cumulative environment selections, and task observation count; it then applies Eq. 5 using the informativeness score and batch similarity penalty. The hard constraints are parameterized by a per-round environment cap C1, a rolling three-step environment cap C3, and a consecutive-task cap 

Ctask , set to C1 = 4 , C3 = 11 , and Ctask = 2 in our experiments. The progress filter is part of candidate eligibility. It uses adjacent observations of the same task as training transitions. A ridge predictor estimates the later mean reward from the earlier mean reward, squared mean reward, variance, training step, observation count, and environment category. Each transition is predicted using only transitions from earlier completed training steps. The task’s residual history is combined with environment and relation-neighbor references. A task with at least three scorable transitions and a non-positive estimated residual is removed from the exploitation candidates. It remains eligible for coverage and can return to exploitation after new observations change its estimate. The identifier filter is also part of candidate eligibility. It examines high-reward trajectories for identifiers that cannot be obtained from the permitted context or for replacement objects that duplicate existing records. It first replays the saved fixed action sequence and checks that the replayed reward agrees with the stored reward within 10 −4. It then removes the suspicious action and dependent edits and replays the sequence again. A task is filtered only when the removal lowers the reward. Replay uses the saved actions and does not sample a new model trajectory. At cold start, EnvSched selects one representative task from each environment using the highest mean within-environment similarity. It fills the remaining slots by combining global novelty and within-environment novelty, with no more than two tasks from each environment in the first batch. This initialization uses static structure only.

The task pool contains 2,550 task instances from 51 environments. The default batch contains 

B = 64 environment–task pairs, with eight rollouts per pair. We use a fixed coverage fraction ρ = 0 .5,giving 32 coverage slots and 32 exploitation slots. The within-environment and cross-environment neighbor sizes are 6 and 12, respectively; the two relation estimates use fixed equal fusion weights of 

0.5 each, and the graph estimate and task-history prior use shrinkage strengths λg = λs = 2 . The

long and short half-lives are hlong = 8 and hshort = 2 training steps, the recent-decline coefficient is 

ηdecline = 0 .5, the exposure-count scale is c0 = 16 , and the batch similarity penalty is λsim = 0 .08 .Environment caps are C1 = 4 , C3 = 11 , and Ctask = 2 . These hyperparameters are fixed across model sizes. The six view weights are (0 .28 , 0.08 , 0.16 , 0.12 , 0.16 , 0.20) . The six static views use word unigrams and bigrams, character 3–5-grams, verifier-check text, verifier code structure, initial task context, and the complete operation description. The structured operation description is extracted offline and normalized for the cross-environment representation. Numeric values are normalized into abstract categories so that cross-environment similarity reflects operation and condition types instead of exact identifiers. 

E Cross-Environment Graph Construction Prompt 

This appendix provides the complete prompt used to construct cross-environment edges in the dual-relation graph (Section 2.2). Within-environment edges use TF–IDF over concrete features like tool names and verifier code. Cross-environment edges require an abstract representation that removes domain-specific identifiers.  

> E.1 What This Prompt Extracts

Given a task specification (instruction, initial state, verifier checks, available tools), the prompt outputs a structured description of what operations the task requires and how they depend on each other. After removing domain-specific identifiers, this structure becomes the cross-environment similarity Sabs in Eq. 1. The prompt outputs five components: 1. Operations : The atomic actions required to complete the task. Each operation is labeled with a type that describes its effect: • lookup : retrieve data from the environment (e.g., “find user record by username”) • update : modify existing records (e.g., “change user status field to active”) • create : add new entities to the environment (e.g., “create new reservation”) • delete : remove records • validate : verify constraints without changing state • authorize : check permissions Each operation lists which other operations must complete before it can start. For example, “update_user_status depends on lookup_user because the user ID from lookup is needed as input to update.” 2. Gates : Logical conditions that must be satisfied before operations can proceed. If a gate cannot be satisfied, all operations depending on it are blocked. Three examples illustrate the concept: • Identifier resolution gate: The task says “update status for user Alice”, but the update operation requires a numeric user ID, not a name. A gate captures this requirement: the user ID must first be obtained by looking up “Alice” in the user table. 

> 18

• State precondition gate: The task says “assign patient to bed 301”, but the assignment operation requires that bed 301 is currently unoccupied. A gate captures this requirement: the bed’s occupancy status must be checked before assignment can proceed. • Authorization gate: The task says “delete the billing record”, but the delete operation requires admin privileges. A gate captures this requirement: the agent must have the required permission, which may not be available in the current environment. Each gate also records its provenance (where the required information comes from): • task_literal : the task instruction directly supplies the value (e.g., “update user ID 42”) • unique_lookup : a tool call deterministically finds it (e.g., username “alice” matches exactly one user) • broad_lookup : multiple records match; the agent must choose (e.g., name “John Smith” matches 3 users) • prior_tool_output : an earlier operation produces it (e.g., create_user returns the new user ID) • agent_generated : the agent must create the value (e.g., generate a password) • unavailable : no available tool can obtain it 3. Dependencies : Directed edges stating which operations must finish before others can start. For example, if operation B needs the output of operation A as input, then B depends on A. This is recorded as an edge from A to B in the operation graph. 4. Reward groups : A partition of the verifier checks (the success conditions for the task). Verifier checks that are controlled by the same operation or gate belong to the same group, because they will succeed or fail together. Three examples: • Suppose the verifier has three checks: “user status is active”, “user last_login timestamp is updated”, and “user notification_sent flag is true”. If all three fields are written by the same update_user operation, the three checks belong to one group with relation type 

shared_operation .• Suppose two verifier checks both examine properties of a user record, and obtaining that user record requires satisfying an identifier-resolution gate. If the gate fails, both checks fail. They belong to one group with relation type shared_gate .• Suppose one verifier check examines a field that already has the correct value in the initial state, and no operation in the task will modify it. This check is already satisfied before the agent does anything. It belongs to a group with relation type initially_satisfied .5. Conflicts : Pairs of operations that have ordering constraints or incompatibilities beyond simple data dependencies. Three conflict types: • order : Operation A must execute before operation B, even if B does not directly consume A’s output. For example, “verify eligibility must precede commit transaction” ensures that invalid transactions are never committed, even though the commit operation does not use the verification result as a data input. 

> 19

• mutual_exclusion : Operations A and B cannot both execute in the same task. For example, “approve request” and “reject request” are mutually exclusive: completing the task requires executing one or the other, but not both. • destructive : Operation A removes the preconditions needed by operation B. For example, delete_user makes any subsequent update_user impossible because the user record no longer exists. After extraction, we apply a deterministic abstraction procedure to the output: 1. Replace each tool name with its operation type (e.g., get_user_by_name → lookup ,

update_user_status → update )2. Remove all entity identifiers (user IDs, record keys, table names) 3. Remove all database field names (e.g., status , assignment_id )4. Replace literal values with type placeholders (e.g., “active” → <string> , 42 → <int> )5. Retain the dependency structure, gate types, and group relations This produces an abstract structure description. For example, a task “update user Alice’s status to active” with concrete extraction [lookup(get_user_by_name, input=Alice), update( set_user_status, target=user_id, value=active)] becomes abstract structure [lookup( type=entity_by_name), update(type=entity_field)] after applying these replacements. The abstract string is TF–IDF encoded to produce gi in Eq. 1, which computes cross-environment similarity Sabs
