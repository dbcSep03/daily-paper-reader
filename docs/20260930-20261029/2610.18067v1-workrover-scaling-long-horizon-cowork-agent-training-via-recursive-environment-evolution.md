## 摘要
扩展交互式环境对于通过强化学习训练长时程智能体至关重要。这些环境在初始生成后通常还需要进一步测试与细化，而修正任务中的缺陷也可能需要更新其工作上下文和验证器。然而，现有构建流水线在保持这些组件对齐的同时，对这类迭代细化提供的支持有限。我们提出 WorkRover，一个通过递归环境演化训练长时程协作智能体的框架。其由执行框架驱动的合成机制使构建智能体能够联合构建并验证语义对齐的工作上下文、可执行任务和基于证据的验证器，并根据工作区状态和执行反馈调整其动作，而不是遵循固定的构建流程。为支持环境演化，我们引入因子兼容性回放（Factorial Compatibility Replay, FCR），它利用 rollout 反馈，通过依赖闭合回放评估组件修订的组合，并在保持任务要求和评估约束的同时，从测试过的候选方案中选择最小的已验证修复。为提供更细粒度的训练信号，我们提出验证器到轮次的信用分配（Verifier-to-Turn Credit Assignment, VTCA），它利用确定性工作区进展检查的信号增强轨迹级 GRPO 优势，并基于记录的工具输出和产物依赖关系，将有限比例的正向进展信用分配给前置轮次。使用 WorkRover，我们对 Qwen3.5-35B-A3B 进行后训练，得到 WorkRover-35B-A3B，并在多个协作智能体基准上对其进行评估。其报告得分在 JobBench 上超过 Qwen3.5-35B-A3B 26.27 个百分点，在 OfficeQA Pro 上超过 29.32 个百分点，在 GDPval v2 上超过 413.25 Elo 分。这些结果表明，WorkRover 为长时程协作智能体的可扩展训练提供了有前景的基础。

## Abstract
Scaling interactive environments is important for training long-horizon agents through reinforcement learning. These environments often require further testing and refinement after initial generation, and correcting defects in a task may also require updating its work context and verifier. However, existing construction pipelines offer limited support for such iterative refinement while keeping these components aligned. We introduce WorkRover, a framework for training long-horizon cowork agents through recursive environment evolution. Its harness-driven synthesis enables construction agents to jointly build and validate semantically aligned work contexts, executable tasks, and evidence-grounded verifiers, adapting their actions to workspace state and execution feedback rather than following a fixed construction workflow. To support environment evolution, we introduce Factorial Compatibility Replay (FCR), which uses rollout feedback to evaluate combinations of component revisions through dependency-closed replay and selects the smallest validated repair among tested candidates while preserving task requirements and evaluation constraints. To provide finer-grained training signals, we propose Verifier-to-Turn Credit Assignment (VTCA), which augments trajectory-level GRPO advantages with signals from deterministic workspace-progress checks and assigns a bounded share of positive-progress credit to prerequisite turns using recorded tool-output and artifact dependencies. Using WorkRover, we post-train Qwen3.5-35B-A3B to obtain WorkRover-35B-A3B and evaluate it on several cowork-agent benchmarks. Its reported scores exceed those of Qwen3.5-35B-A3B by 26.27 percentage points on JobBench, 29.32 percentage points on OfficeQA Pro, and 413.25 Elo points on GDPval v2. These results suggest that WorkRover offers a promising foundation for scalable training of long-horizon cowork agents.

## 二、方法论

### 2.1 总体框架

- 将训练环境组织为 N 个任务包：\(\mathcal{L}=\{P_i=\langle C_i,T_i,V_i\rangle\}_{i=1}^{N}\)，其中 \(C_i\) 为工作上下文（文件、能力、应用环境），\(T_i\) 为任务（目标、交付物、约束），\(V_i\) 为验证器。
- 由 **Harness \(\mathcal{H}\)** 统一协调构建、跟踪依赖并管理执行，贯穿三个阶段。
- 整体由三部分组成：**Harness 驱动环境合成**（§3.1）、**因子兼容性回放 FCR**（§3.2）、**验证器到轮次信用分配 VTCA**（§3.3）。

### 2.2 Harness 驱动的环境合成（三阶段）

- **Phase I：工作上下文构建**
  - **文件上下文**：从项目仓库、DeepResearch 轨迹、文档与产物中收集文件，过滤后对语义、跨文件关系、类型、可编辑性做画像，形成通用与领域文件池（10 万+ 通用、20 万+ 领域）。
  - **能力上下文**：打包已安装技能与插件及其 MCP 接口、工具、脚本、参考资料，形成 job / file / app 三类技能库（21,444 个 app 技能、5,918 个 file 技能、36,064 个 job 技能，覆盖 317 个职业角色）。
  - **应用上下文**：对 mock 与真实安装的应用做插桩，构建具备运行时、UI 观察、交互接口与 reset 能力的可执行 App WorkEnv（2k+）。
- **Phase II：长时程任务合成**
  - 用**构建配置（construction profile）**控制编辑范围（约 10 / 20 / >30 个文件）、交互轮次（5–10 / 15–30 / >30）、技能组合复杂度、干扰项比例（10%/20%/30%）、跨环境依赖数（2/3/4）等。
  - **Skill Matcher** 从 job skill 出发，匹配文件与应用的输入输出接口，组合成内部工作流，其依赖图指导 **Starter WorkEnv** 的组装，并标注可编辑与受保护状态。
  - 独立的 **Demonstrator Agent** 从初始状态执行任务；成功即确认可行性并产生 **Reference State**。任务指令、Starter WorkEnv、Reference State 共同构成候选。
  - 通过**输入消融**检验依赖必要性；独立确认的兼容性问题触发 FCR。
- **Phase III：验证器合成与校验**
  - 先从任务指令与智能体可见的工作区条件导出**评估契约（Evaluation Contract）**，并在查看 Reference State **之前**固定：预期结果、允许编辑、受保护状态、关键标准、可采信证据。
  - 据此生成 rubric 与验证规则，将每条标准绑定到文件、应用状态或状态差异的证据上。
  - **四层验证**：基础设施有效性（Infrastructure Validity）→ 规范状态差异（Canonical State Diff）→ 功能检查（Functional Checks）→ 语义 Judge（仅处理可执行检查无法覆盖的标准）。
  - **校准**：验证器必须拒绝 Starter State 与违反契约的负例，接受 Reference State 与独立获得的合法替代方案；通过后冻结，进行一次性准入测试，失败即拒绝且不反馈修复。
  - 通过者成为准入包 \(P_i\)，保留被接受的执行轨迹 \(\tau_i\) 用于训练。

### 2.3 因子兼容性回放（FCR）

- **诊断与提案**：先区分“环境问题”与“智能体自身决策错误”，后者不触发环境修改。对环境问题，Harness 记录受影响版本与依赖，冻结任务要求与验证规则，并为每个可用组件冻结**一个**修复提案：\(\Delta C,\Delta T,\Delta H,\Delta V\)。
- **组合枚举**：对 \(d\le 4\) 个可用组件，每个组合 \(\chi\in\{0,1\}^d\) 表示是否应用对应提案，最多 \(2^d\le 16\) 种。
- **依赖闭合**：每个组合扩展为 \(\Gamma(\chi)=\mathrm{Close}(\chi)\)，即除选中修复外，还包含为保持依赖组件兼容所必需的连带更新。
- **Harness 筛选与回放**：先剔除在依赖、资源绑定或需求上已确认冲突的组合；剩余组合在**相同策略、执行预算、随机种子**下重建并回放，从而区分“单独修”与“联合修”的差异。
- **修复选择**：独立检查必须确认原问题已解决、任务要求与信息边界未变、受影响任务无回归，且验证器能拒绝已知失败、接受合法替代；**不得用智能体成功率或候选验证器给出的分数作为解决证据**。在通过检查的组合中，选择 \(\Gamma(\chi^\star)\) **改动组件版本数最少**者；并列时优先更少重建依赖，再取更低成本。
- **确认与更新**：用新随机种子做 fresh rollout 确认；未准入候选从最早受影响步骤重走验证，已准入包在确认后整体生效；失败则丢弃候选或保留上一已准入版本。后续 rollout 可暴露新错位并启动下一轮演化。

### 2.4 验证器到轮次信用分配（VTCA）

- **轨迹监督**：先用验证通过的示范做 SFT，再对同一任务与初始状态采样 RL rollout。有效评估的终端奖励为 \(R_{i,r}=G_{i,r}[(1-\lambda)S_{B,i,r}+\lambda S_{A,i,r}]\)，其中 \(G\) 为完整性/受保护状态/安全检查门，\(S_B\) 为结果分，\(S_A\) 为
