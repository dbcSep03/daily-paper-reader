## 摘要
AI 协作伙伴必须协调工具、跨轮次沟通，并在遵守工作流约束的同时对不断变化的工作区状态采取行动。为这些能力构建训练经验需要连贯的请求、服务记录、工具接口和评分检查。我们提出 CoworkEnv，一个能力引导的框架，用于为 AI 协作伙伴合成可执行训练环境。工作流需求指导任务构建，而带有反馈修复的程序化验证会检查生成的规范与评分行为。教师执行产生经过整理的演示，用于监督微调（SFT）；学生交互则提供用于强化学习（RL）的 rollout 和奖励。利用这些资源，我们训练紧凑的 PocketWorker 模型。对于 Qwen3-VL-8B-Instruct，SFT 在 Claw-Eval 上将平均得分从 46.6 提升至 64.1，其中在多轮任务上获得 31.9 分的提升。将仅使用 SFT 的方案扩展到 ClawMark，展示了其在协作伙伴基准上的适用性。我们进一步比较了在奖励处理和信用分配上有所不同的配置下的 RL 训练动态。训练奖励的提升提供了初步证据，表明所构建的环境支持策略优化。

## Abstract
AI coworkers must coordinate tools, communicate across turns, and act on changing workspace state while respecting workflow constraints. Constructing training experience for these capabilities requires coherent requests, service records, tool interfaces, and grading checks. We present CoworkEnv, a capability-guided framework for synthesizing executable training environments for AI coworkers. Workflow requirements guide task construction, and programmatic validation with feedback repair checks generated specifications and grading behavior. Teacher executions yield curated demonstrations for supervised fine-tuning (SFT), while student interactions provide rollouts and rewards for reinforcement learning (RL). Using these resources, we train compact PocketWorker models. For Qwen3-VL-8B-Instruct, SFT raises the mean score from 46.6 to 64.1 on Claw-Eval, including a 31.9-point gain on Multi-turn tasks. An SFT-only extension to ClawMark demonstrates applicability across coworker benchmarks. We further compare RL training dynamics across configurations that vary reward processing and credit assignment. Improving training rewards provide preliminary evidence that the constructed environments support policy optimization.

## 1. 核心问题与研究动机

- **背景定位**：AI“协作伙伴”（coworker agent）需要在多轮对话中协调多个工具、读取分散在各类业务系统中的记录、在变化的工作区状态上执行操作，并遵守权限与流程约束（如客服工单处理、支付变更调查）。
- **核心痛点**：这类长时程任务的训练经验极难构造。一个可用任务必须让**请求、证据、可用动作、评分标准**四者自洽：
  - 同一客户在不同服务中的记录必须一致；
  - 工具必须暴露完成任务所需的信息，并实现预期的状态变更；
  - 评分必须能判断“目标更新是否真的发生”“禁止动作是否被避免”——仅凭一段看似合理的最终回复无法验证。
- **因此**：可执行环境的构建与验证，是数据合成不可分割的一部分，而非附属工程。
- **研究问题**：如何把“目标能力”系统地翻译成可执行训练任务，并同时支撑**模仿学习（SFT）**与**交互学习（RL）**？
- **整体含义**：论文主张“环境即数据”——把环境构造与解题尝试生成解耦，用同一套任务定义同时产出教师示范与学生 rollout，从而让小参数模型（8B/4B）在协作工作流上取得可观提升。

## 2. 方法论

### 2.1 核心思想

以**能力引导（capability-guided）**的方式，把开发者选定的能力需求 → 覆盖计划 → 工作流规格 → 可执行任务包（请求 + 初始服务记录 + 工具接口 + 评分检查）→ 教师执行/学生交互 → SFT 数据或 RL 环境。

### 2.2 任务形式化

任务表示为四元组：

- **T_i = (u_i, s_i⁰, A_i, G_i)**：u_i 为用户请求，s_i⁰ 为初始状态（服务记录/世界状态），A_i 为工具接口集合，G_i 为评分检查（完成检查 + 禁止动作）。

### 2.3 任务合成流程

- **覆盖计划**：每个计划槽包含 7 个字段——`task_id`、`services`、`category`、`difficulty`、`language`、`mock_today`（固定参考日期，锚定时间敏感条件）、`scenario`（目标、选择条件、干扰项、动作约束）。
- **LLM 生成规格**：输入计划槽 + 服务目录（工具与记录格式）+ 输出格式规范 + 示例任务，输出用户请求、初始记录、结构化完成检查、禁止动作列表。
- **程序实例化**：服务配置从注册表填充；完成检查与禁止工具被序列化进**固定评分模板**，实现“任务变化、执行与评分代码复用”。
- **跨服务信息链接**：证据分散到多个服务（如 CRM 客户标识 ↔ 工单 ↔ 知识库流程 ↔ 邮件收件人）；设置**干扰项**（如“看起来紧急但不满 48 小时”的高优先级工单）；评分检查引用同一规格中的实体与工具参数/审计记录。
- **安全场景（Generator–Discriminator 双角色）**：Generator 起草请求与记录；Discriminator 在**独立上下文**中只接收记录 + 安全注记（不含完整请求文本），据此定义完成检查与禁止动作，降低评分泄漏与自我偏袒。

### 2.4 验证与反馈修复

- **规格级检查**：JSON 可解析、所选服务已注册且有初始记录、完成权重之和为 1、必需工具集与禁止工具集不冲突、**请求级标识符泄漏检查**（答案标识不得出现在用户请求中，保留“必须通过交互发现”的难度）。
- **评分一致性门（grading-consistency gate）**：用合成工具调用 + 服务审计记录反向测试评分器——满足条件的记录必须得满分且 safety=1；空记录 completion 必须为 0；在完整记录上追加一次禁止调用必须使 safety=0。
- **反馈重生成**：失败诊断回传生成器，每个计划槽最多 2 次尝试（初始 + 1 次重试），仍失败则丢弃；通过者连同记录、服务配置、评分代码打包。

### 2.5 教师执行与数据整理

- 教师在 Harbor 框架下通过 Claude Code 适配器执行任务，轨迹记为 **τ_ij = (u_i, a_1, o_1, …, a_L, o_L)**，评分器打分并保留工具参数、观测、任务/试验 ID。
- **任务级分组**（按平均完成度 c̄_i）：
  - TRIVIAL（c̄ ≥ 0.999）：仅保留每个“归一化任务前缀”的第一条合格记录，避免简单任务重复监督；
  - UNSOLVABLE（c̄ ≤ 0.001）：弃用；
  - KEEP（中间区间）：可贡献多条示范。
- **导出奖励阈值**（按来源分别设定）：混合池 0.5、多服务/安全专用导出 0.80、文档抽取 0.999、ClawMark 转换 0.3。
- **结构过滤**：去除无法构成有效 user–assistant 交互的记录、少于 5 条消息、超过 20 次工具调用、整例超过 40,000 字符；单条工具观测截断至 1,000 字符。
- **实测转换**：1,809 条混合候选 → 937 条示范（淘汰 494 条无有效交互、142 条过短、140 条工具调用过多、96 条超字符预算），产出平均奖励 0.862、平均 13.8 条消息、6.8 次工具调用。

### 2.6 训练接口

- **SFT**：将整理后的消息序列套入学生 chat 模板，**仅对 assistant 回复与工具调用计算损失**，用户消息与工具观测作为上下文；损失为掩码 token 的负对数似然按掩码 token 总数归一化（等权监督）。
- **RL**：任务引用加载请求/记录/工具/评分器，学生**自行在线交互**生成轨迹，评分器依据调用与审计记录给奖励；缺失奖励的样本中止，失败/不完整的 rollout 组被拒绝重试后再做优势估计。
- **两接口共享**任务定义、服务实现与评分机制，区别仅在数据选择策略。

## 6. 主要结论与发现

1. **“环境即数据”在小参数模型上成立**：8B 与 4B 模型经环境合成数据 SFT 后，在 Claw-Eval 与 ClawMark 上均优于各自 base，说明**任务定义的可执行化 + 评分可验证化**能够把“协作工作流能力”转化为有效的监督信号，而不必依赖更大参数量。
2. **数据量呈单调增益**：20% → 50% → 100% 的比例消融显示性能随数据量单调上升，且未出现明显饱和，提示当前瓶颈更可能在**任务覆盖度**而非数据冗余。
3. **教师轨迹需要“难度分层”而非“全量保留”**：TRIVIAL 任务仅保留前缀首条、UNSOLVABLE 任务直接弃用，这一分组策略实质是在做**信息密度筛选**；实测 1,809 → 937 的淘汰率（约 48%）说明原始教师轨迹中近半数不具监督价值，管线中的过滤环节是性能的必要条件而非可选优化。
4. **RL 相对 SFT 有进一步提升但证据强度有限**：四种 GRPO 系变体在多数任务分组上高于 SFT 热启动点，奖励曲线整体上行、响应长度增长，符合在线交互学习预期；但作者明确将其定位为“初步证据”，且方法间因归一化方式不同不可直接比较，因此**不能据此宣称某一 RL 算法更优**。
5. **评分一致性门是质量控制的关键环节**：以“合成正确记录必得满分、空记录必得 0、追加禁止调用必使 safety 归零”三向反测评分器，把“评分器本身是否有判别力”纳入自动化验证，这一做法比仅校验 JSON 格式更能保证 RL 奖励信号的可信度。
6. **规格级泄漏检查保护任务难度**：强制答案标识不出现在用户请求中，确保模型必须通过多轮工具交互发现证据，避免任务退化为“读题即答”，这是长时程任务合成中容易被忽视但影响很大的设计约束。

## 7. 局限性与批判性讨论

- **算力与成本透明度不足**：未报告 GPU 型号/数量/时长，也未给出教师执行的 API 调用次数与费用。对于一篇以“资源受限研究者可复现”为卖点的论文，这是最实质的缺口——读者无法估算复现门槛。
- **统计稳健性薄弱**：主表为单次训练结果，无多种子、无置信区间、无显著性检验；在 199 与 100 任务规模下，单次评估的方差可能掩盖方法间的小幅差异。
- **RL 对照的实验设计不严谨**：作者自承 batch size、优势归一化、损失归一化在不同方法间不一致，GiGPO 缺少 ω=0 的消融，导致“RL 方法比较”更接近工程性试跑而非受控实验。
- **评分器的覆盖边界未被检验**：完成检查由 LLM 生成后序列化进固定模板，但论文未讨论**检查项遗漏**（真实完成但未被检查覆盖）与**检查项过严**（合理变通被判失败）两类错误率，也未做人工复核的一致性统计（如与人类评分的 Cohen's κ）。
- **安全维度停留在机制描述**：安全任务的构造依赖 Discriminator 的独立上下文，但缺少对 Discriminator 自身偏差、以及“禁止动作”集合是否覆盖真实合规风险的量化分析。
- **任务生态效度未知**：服务目录与记录格式为模拟构造，虽保证了内部一致性，但与真实企业系统（权限模型、异步状态、部分可观测）的差距未被讨论；跨领域迁移（ClawMark 13 个专业领域）仅给总分，未按领域拆解，难以判断能力是普适还是集中于少数领域。
- **语言与多模态覆盖不对称**：覆盖计划含 `language` 字段，但实验以英文任务为主；Multimodal 仅出现在 RL 对比的 All tasks 分组中，SFT 侧未见多模态结果。

## 8. 启示与实践建议

- **对数据工程**：把“可执行环境 + 可验证评分”前置到数据合成阶段，比“先生成对话再人工筛”更可控；规格级校验 + 评分一致性门构成两道低成本自动闸门，值得作为通用范式复用。
- **对训练策略**：难度分层（TRIVIAL/UNSOLVABLE/KEEP）与按来源设定差异化奖励阈值，本质是对监督信号做**信噪比管理**；在数据有限时，这一环节的收益可能高于调参。
- **对 RL 落地**：需先保证评分器的判别力，再谈算法选择；在线 rollout 的失败组重试与缺失奖励中止机制，是维持优势估计无偏的必要工程细节。
- **对论文写作**：若要支撑“小模型可做协作 agent”的主张，建议补充多种子方差、按领域/安全类别的分层结果，以及与通用指令数据的等预算对照。

## 9. 总体评价

论文的核心贡献不在单一模型指标，而在**提出并工程化了一条“能力 → 覆盖计划 → 可执行任务 → 教师示范/学生 rollout → 训练接口”的完整链路**，并用 8B/4B 两个规模、两个 benchmark 与一组数据比例消融提供了方向性证据。其方法论价值在于把“环境构造”从附属工程提升为一等公民，并用评分一致性门解决了合成数据中“看似合理但不可验证”的通病。

主要短板集中在**实证严谨性**：算力不透明、单种子、RL 对照非单变量、安全评估缺量化。这些并不否定其范式意义，但意味着文中“小模型可胜任协作工作流”的结论应被理解为**在特定模拟服务生态与特定评分体系下的可行性证明**，而非可直接外推的通用能力声明。
