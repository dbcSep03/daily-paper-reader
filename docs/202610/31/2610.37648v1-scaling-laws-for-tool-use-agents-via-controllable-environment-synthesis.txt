Scaling Laws for Tool-Use Agents via
Controllable Environment Synthesis
Andrew Szot, Samira Abnar, Omar Attia, Abbas Kazerouni, Michael Kirchhof, Cheng-Yu Hsieh, Raviteja
Vemulapalli, Alexander Toshev
Apple
We explore how to build performant large language model (LLM) tool-use agents that complete complex, multi-step tasks.
Specifically, we study how data composition in synthetically generated tool-use environments affects the training of such
agents. To do so, we propose the SynthAPI pipeline, which explicitly controls the diversity of generated environments
along the axes of tools, tasks, and the databases on which the tools operate. By systematically varying SynthAPI’s gen-
eration controls in 458,752 tasks across 849 trained models of four different sizes, we derive a scaling law that predicts
downstream tool-use agent generalization based on the scale and composition of the synthesized environments. These
predictable relationships reveal several lessons for scaling tool-use agent data. As data budgets grow, scaling tool and
database diversity becomes more effective than increasing the number of tasks, and increasing data complexity yields
larger gains. Scaling according to these findings yields agents that outperform models trained on data from prior work in
large-scale tool-use agent and synthetic environment generation across four evaluation benchmarks.

Introduction
Large language models (LLMs) have demonstrated impressive capabilities as tool-use agents that interact
with complex, stateful environments (Trivedi et al., 2024; Patil et al., 2025). Such agents must select and
compose tools over multiple steps while tracking state changes and generalizing to new environments with
new APIs. Progress in developing such agents depends on scaling high-quality, diverse training data. Yet
producing this data is challenging because multi-step tool interactions are scarce in internet text and require
realistic tasks, diverse tools, and rich environment data.
Prior work addresses this challenge by using LLMs to synthesize tool-use data. While many existing works
focus on synthesizing tool-use data to train stateless, read-only tool-use agents (Schick et al., 2023), work
on scaling supervision for stateful tool-use agents is more limited. Some approaches use LLMs to synthesize
entire tool-use trajectories, including simulating the tool responses (Liu et al., 2024a; Tang et al., 2023).
These techniques have demonstrated impressive scaling (NVIDIA, 2025; Lee et al., 2026), but complex tool
outputs and state transitions can be difficult to simulate reliably. Other approaches synthesize code-backed
executable tool environments (Wang et al., 2026; Song et al., 2026; Xu et al., 2026; Dong et al., 2026).
However, these efforts primarily emphasize increasing data quantity, leaving open which properties of the
generated data drive downstream performance. Tool-use agent data varies in the diversity of available tools,
the tasks they support, and the database states over which they operate. Understanding how these properties
affect generalization is necessary to determine what data to generate as training scales.
To study these relationships, we introduce SynthAPI, a controllable synthesis pipeline for multi-step tool-
use environments. SynthAPI uses LLMs to implement apps comprising Python tools that read and modify

generalization changes with scale.
Comparisons at fixed task budgets show that, as these budgets grow,
expanding tool diversity becomes more valuable than generating additional tasks within the same set of
tools. Furthermore, repeating the same tasks with different data profiles also becomes more important than
generating new tasks. Training with more complex data profiles also yields larger gains at higher budgets.
These findings emphasize the importance of tool and data profile diversity over simply increasing the number
of tasks. We propose an environment composition dependent scaling law that captures these effects. Across
four model sizes, we hold out the runs in the top 25% of training FLOPs and show that the law extrapolates
to them, including runs with up to 16× the largest FLOP budget used for fitting, achieving a mean absolute
error of 0.0285 on the normalized downstream score, compared with 0.1706 for a scaling model that relies on
the number of tasks alone and ignores the composition of environment properties.
With the optimal environment composition recipe determined by our proposed method, we show SynthAPI
transfers to broad tool-use agent benchmarks across AppWorld, BFCL, and ASTRA-Bench (Trivedi et al.,
2024; Patil et al., 2025; Xiu et al., 2026).
At a fixed data budget, the recipe identified by our analysis
outperforms a suboptimal recipe that simply relies on scaling the number of tasks alone across all model
sizes and benchmarks. We find that agents trained on the SynthAPI data outperform agents trained on
prior large-scale tool-use agent data (NVIDIA, 2025) by 30.5 percentage points on average across the three
benchmarks. We also compare SynthAPI to strong per-benchmark data synthesis baselines, outperforming
the strongest baseline at each model size by 7.6–11.6 percentage points on AppWorld Test-Challenge and
2.0–3.7 points on BFCL (Lee et al., 2026; Xu et al., 2026; Song et al., 2026). These results demonstrate the
importance of properly scaling the data composition of synthesized environments through our scaling law
enabled by the controllable environment generation in SynthAPI.

Related Work
Synthetic supervision has been widely used to train LLMs for tool use. Early methods train on demonstrations
over predefined API collections (Schick et al., 2023; Qin et al., 2023; Chen et al., 2024), while subsequent work
generates supervision through live APIs and executable functions (Liu et al., 2024b; Prabhakar et al., 2025).
Other approaches simulate API responses with LLMs (Liu et al., 2024a; Tang et al., 2023) or combine data
from multiple sources and synthesis pipelines (Zhang et al., 2025). DIVE (Chen et al., 2026) analyzes tool
diversity in evidence-based question answering, whereas SynthAPI studies multi-step read-write workflows
over structured databases, a setting emphasized by recent tool-use agent benchmarks (Trivedi et al., 2024;
Patil et al., 2025). Nemotron-Agentic (NVIDIA, 2025) scales LLM-simulated tool interactions to 335k trajec-
tories. SimSAT (Lee et al., 2026) extends such simulation to long-horizon tasks. However, these simulators
rely on an LLM to generate every tool response, making increasingly complex outputs and state transitions
difficult to simulate reliably. Thus, unlike these works, SynthAPI scales tool data through database-backed
executable environments.
Like SynthAPI, recent work also synthesizes executable tool-use environments backed by persistent databases
(Wang et al., 2026; Song et al., 2026; Xu et al., 2026; Dong et al., 2026). Unlike these works, SynthAPI
couples this synthesis with explicit controls over the diversity and complexity of tools, task instructions, and
initial database states. These controls let us disentangle how training-data composition affects downstream
generalization. Our analysis goes beyond prior scaling studies that primarily vary the number of synthesized
environments or examine domain diversity at a fixed task count (Tu et al., 2026). Specifically, we study how
to allocate a fixed data budget among new tools, additional tasks for existing tools, and alternative database
states for existing tasks.
We further derive a joint scaling law that extrapolates aggregate downstream
generalization to larger compute budgets and predicts which data allocations maximize performance. We
use these predictions to design a training recipe that improves agent performance over prior synthetic-data
generation approaches.
Scaling laws characterize predictable relationships between model quality, model size, data volume, and
training compute. Early work established power-law behavior in language-model pre-training, while compute-
optimal analyses studied how a fixed budget should be divided between parameters and tokens (Kaplan et al.,
2020; Hoffmann et al., 2022). Related studies extend scaling analysis to transfer learning, fine-tuning, and
reinforcement-learning post-training (Hernandez et al., 2021; Tan et al., 2025). For tool-use models, prior
work develops scaling laws for pre-training with agent data, using benchmark loss as the prediction target
(Zhuang et al., 2025). In contrast, SynthAPI predicts downstream task success from environment-generation
factors, relating generalization to the scale, and diversity of generated tools, tasks, and data profiles.

SynthAPI: Synthetic Environments for Tool-Use Agents
SynthAPI is a controllable pipeline for synthesizing interactive tool-use agent environments.
SynthAPI
consists of two stages where first apps consisting of APIs and databases are coded in Python and next tasks
are constructed using the functionality in these apps.
3.1
API Generation
In the first phase of creating synthetic tool-use agent tasks, SynthAPI generates a wide diversity of tools to
base tasks on. SynthAPI does this by synthesizing “apps”, which are a coherent collection of interacting tools
that can be composed to solve realistic tasks. This organization naturally produces dependencies among tools
and mirrors deployment settings in which agents use tools to accomplish user goals. These apps are each
independently implemented in Python code from scratch by an LLM, which we term the “builder LLM”. We
use Gemini-3.1 Pro (Google DeepMind, 2026) with internet access disabled as the builder LLM. We manually
define a broad app taxonomy consisting of shopping, music, productivity, finance, fitness, messaging, utilities,
and social.
The builder LLM starts to generate an app by generating “metadata” consisting of the app
name, a short app description, the taxonomy category the app belongs to, and a list of functionalities. The
functionalities are short descriptions of interactions possible in the app, such as “Initiate a return” or “Apply
a promo code to your shopping cart” in the case of a shopping app.
3


Next, SynthAPI generates a database schema for the app from the metadata to ground app functionality in
complex stateful interactions. For example, in a shopping app there need to be products, inventory, users,
addresses, payment methods, reviews, carts, and orders for the tools in the app to implement meaningful
behaviors. Given the app metadata, the builder LLM generates a db.py file that contains Python Enum and
dataclass definitions defining all data types necessary to instantiate the provided app functionalities. These
classes only specify data formats rather than instantiated database states. The final step of app creation is
generating an API layer that operates on the database schema. From the contents of db.py and the app
metadata, the builder LLM generates an apis.py file for the app. The API file consists of a set of Python
functions defining the possible operations in the app. Each function takes as input a database object that
tracks instantiated data schema objects, along with any other input arguments, which may consist of the
defined data types. These functions read or modify instantiated database objects and collectively define the
agent’s available tools. In a shopping app, example resulting APIs may search products, inspect reviewers,
or create an order. Public functions from the API set are exposed to the agent as callable tools.
In summary, in the first phase, SynthAPI generates a set of apps, each of which contains app metadata,
a data schema Python file, and an API definition file. All components are generated from scratch by the
builder LLM. See Section A.1 for all details and prompts on app generation.

Ultimately, SynthAPI creates environments consisting of tools A = {a1, . . . , aA} and tasks T = {T1, . . . , TN}
within these apps. The key contribution of SynthAPI is controllability of the composition and properties of
the task set (A, T ) via the following controls:
• A number of apps: More apps means more diversity over tools. When generating apps, we ensure an
equal balance across the 8 taxonomy categories previously defined.
• T number of tasks per-app: This is the number of tasks generated based on functionalities within a
particular app. A higher T means more diversity of tasks within an app.
• S number of initial databases per-task instruction. We can keep the same task instruction, verifier,
and oracle solver but vary the initial database state Db0 to form different tasks.
• D amount of distractor data per initial database state.
This is the total number of data batches,
including the core batch Db0
core, that make up the initial database state.
The task set diversity is characterized by A, T, S, producing N = A · T · S total tasks. The data complexity
is characterized by D, which does not change the number of tasks.

Each episode includes a binary verifier, so agents can be directly trained in SynthAPI via reinforcement
learning with verifiable rewards. However, running an RL loop for every setting in our analysis is prohibitively
expensive, so we instead collect trajectories once and then use supervised fine-tuning (SFT) to train on subsets
Ti at the given control settings. We use GLM-5.2 (GLM-5 Team, 2026) as the expert and allow it up to four
attempts per episode. We retain the first attempt for which the verifier indicates successful task completion
and discard episodes for which none of the four attempts succeeds. The task counts used throughout this
analysis thus each have exactly one trajectory. We distill the retained expert trajectories with the standard
next-token prediction objective into student models from the Qwen3.5 family (Team, 2026).
The loss is
applied only to the reasoning and action tokens. By default, we train models for 1 epoch over the dataset.
Training continues until the validation loss increases over a set number of updates, after which we select the
checkpoint with the lowest validation loss for evaluation. This dataset constitutes 5.9B total tokens of which

Task Properties Analysis

data budgets and evaluate downstream generalization on the diagnostic set.

sponds to a different value of S. For each budget N, we use the optimal app-to-task allocation from the
previous study, adjusted for the selected S so that N = T ·A·S. Each task instruction receives its own distinct
data profiles. We fit the model in Equation (4.1) separately for each database count S in place of app count

budgets of 32–512 training instances, one data profile per instruction performs best; at 512–4096, two profiles
perform best; and beyond 4096, four profiles perform best. The fitted performance ceiling also increases
with S. We attribute these gains to learning to solve the same task across different initial database states,
since data manipulation is a key challenge in our training tasks. This suggests that, as the budget grows,
generating additional data profiles for existing instructions becomes preferable to adding new instructions
with new data profiles.
Effect of data complexity: We also study database depth, which controls the amount of distractor data
within each data profile. We compare D = 1, which includes only the minimum state needed to solve the task;
D = 2, which adds a moderate amount of distractor data; and D = 4, which adds a larger distractor set. As
before, the x-axis shows the task budget N, the y-axis shows aggregate downstream performance, and each
curve corresponds to a different D; we use the optimal allocation of A and T with S = 1. Figure 2c shows a
large improvement from D = 1, 2 to D = 4 at high task budgets, indicating that training with distractor data
improves downstream scaling. This pattern may partly reflect the current downstream benchmarks’ limited
sensitivity to increasingly difficult database states. Benchmarks that place greater emphasis on retrieval and
decision-making over dense database states may exhibit different scaling behavior along this dimension.

4.4
Baseline Comparison
Next, we demonstrate the performance of SynthAPI across all the downstream benchmarks and compare
to prior works in task synthesis. For this comparison, we also include performance on the ASTRA-Bench
and BFCLv3 benchmarks. First, to show the value of the FLOP optimal training data composition settings
derived from the previous scaling law analysis we compare to two versions of models trained with SynthAPI
data and a large scale existing tool-use agent dataset:
• SynthAPI-SubOpt: We train one model on 32,768 SynthAPI tasks, but we ignore the lessons from the
previous sections and instead choose A = 32, T = 1024, S = 1, D = 2.
• SynthAPI-Opt: We train under the same task budget as the above, but now maximize app and database
diversity by reducing task prompts, with A = 64, T = 128, S = 4, D = 4.
• Nemotron (NVIDIA, 2025): We train on the full Nemotron-Agentic dataset.
• SynthAPI-Big: We train on the full SynthAPI generated dataset but now for 4 epochs.
The results from Table 1 show the performance of these approaches across all benchmarks. We omit the 2B
size due to its far worse performance in the previous section. First comparing SynthAPI-Opt and SynthAPI-
SubOpt, we see the value of the right data recipe with increasing S, D and A while keeping the total task
budget fixed. SynthAPI-Opt does consistently better than SynthAPI-SubOpt, with especially large deltas
in SynthAPI-Holdout and the 4B model. When scaling up to SynthAPI-Big, results further improve on
most benchmarks with especially large gains in AppWorld. This method greatly outperforms Nemotron,
which contains relatively simple and short-horizon data that does not generalize to the complexity of these
benchmarks and even underperforms the zero-shot starting model in 5 of the 8 settings.
Next, we compare with results reported in prior work in Table 2. On AppWorld, we compare with ToolACE
(Liu et al., 2024a) and ToolAlpaca (Tang et al., 2023), which synthesize tool-use demonstrations with
LLM-simulated API responses, and SimSAT (Lee et al., 2026), which uses LLM simulation to synthesize
long-horizon trajectories. On BFCL, we compare with Agent World Model (Wang et al., 2026), which
synthesizes database-backed tool environments; EnvScaler (Song et al., 2026), which generates environment
skeletons and verifiable task scenarios; and EnvFactory (Xu et al., 2026), which builds executable environ-
ments from real-world resources. Since these BFCL baselines only report results for Qwen3, we also train
SynthAPI-Big on Qwen3-4B/8B.
ToolACE and ToolAlpaca generally underperform the zero-shot models on AppWorld, indicating limited
transfer to its complex stateful tasks. SimSAT, which uses LLM simulation of long-horizon interactions and
GLM-based distillation, provides a substantially stronger baseline. SynthAPI-Big achieves the highest scores
on both AppWorld splits, reaching 66.4% and 77.0% on Test-C at 4B and 9B, respectively, exceeding SimSAT
by 7.6 and 11.6 percentage points. On BFCL, the prior executable environment synthesis methods all improve
over zero-shot, while SynthAPI-Big further surpasses the strongest baseline by 2.0 percentage points at 4B
(EnvFactory) and 3.7 points at 8B (EnvScaler). However, their training regimes differ substantially with
these methods combining SFT and RL on smaller datasets, whereas SynthAPI-Big uses SFT on a much
larger synthetic corpus. These comparisons therefore do not isolate the effect of the synthesis method or
establish relative data efficiency. They do demonstrate that SynthAPI supports large-scale synthesis of tasks
that enable strong downstream generalization. The strong results overall show how our scaling laws can guide

the construction of effective training datasets. See Appendix E for more results on transferring findings to
other datasets, evaluation breakdowns, and further scaling law analysis.
5
Conclusion
This work introduces SynthAPI, a controllable pipeline for synthesizing executable environments for training
and studying tool-use agents. SynthAPI uses LLMs to generate executable environments with a structured
database schema and Python API implementations. SynthAPI then generates verifiable and feasible tasks
with a starting database state. This design allows us to independently scale the diversity of tools, data profiles,
and tasks.
We empirically show that the composition of training data substantially affects downstream
performance. We combine these results in a joint scaling law that predicts downstream performance and
gives optimal data composition settings for a given compute budget. A limitation of SynthAPI is that it
does not simulate a user in the loop that interacts with the agent. Such a setting is important for realistic
settings where agents need to query a user to ask for additional details or clarifying questions. Furthermore,
SynthAPI focuses less on information retrieval tasks involving long and complex documents in realistic user
settings like long email chains or note documents. Since all content in SynthAPI is synthesized from scratch
by the LLM it lacks this semantic depth. Furthermore, the SynthAPI scaling law is only validated on a single
data pipeline and it is not guaranteed to transfer to different data pipelines or training settings.
All tool-use experiments in this work are conducted in research-only simulated environments. The APIs,
tasks, datasets, verifier infrastructure, and training procedures described here do not represent or imply any
deployed Apple product, production system, or product roadmap.

A.3
Agent Interface Details
Each task is a Gymnasium environment (Towers et al., 2024) whose state is the instantiated database and
whose transitions are app API calls. The environment is deterministic, so a trajectory is fully determined by
Db0 and the agent’s actions.
We follow an action format similar to the AppWorld environment (Trivedi et al., 2024): an action is a single
fenced Python code block. It executes in a Python session that persists for the whole episode, so variables
defined on one turn are available on later turns. The app API functions and the episode’s Database object
are bound in the session namespace, so the agent calls tools as ordinary Python functions. A single turn
can therefore call several tools, loop over the records returned by an earlier call, and branch on intermediate
values. Text outside the code block is treated as reasoning and is not executed. If a turn contains no parseable
code block, the environment returns a format error and the turn counts against the step limit.
The observation is the output of the previous code block execution, with tool results returned in JSON
format. When return values are db.py dataclasses, or lists of them, we serialize them field by field into JSON
so that field names and values are explicitly displayed to the agent rather than generic class identifiers. In
other words, when an API returns an instantiated dataclass, the agent sees its full data contents. Errors and
exceptions do not end the episode. Instead, the error message is displayed and the agent can fix the problem
on the next turn. Observations are truncated to 2,048 tokens with an explicit [truncated] marker.
We also expose several “meta-tools” which are always present in the agent’s toolbox. The meta-tools are used
to discover and look up documentation for the dynamic per episode tool set the agent has to deal with.
• list_apps(): name and one-line description of each app in the episode.
• list_tools(app): names and one-line summaries of one app’s public API functions.
• get_tool_documentation(app, tool): one tool’s description, argument names, types and defaults, and
return type.
• complete_task(answer=None): ends the episode, with an optional answer for tasks that require reporting
information rather than only changing state.
Episodes in SynthAPI are capped at 32 steps. The verifier is called only when the agent invokes complete_-
task, so a task counts as a success only if the agent calls complete_task and v then returns true on the
resulting database state. An agent that reaches the step limit without calling complete_task fails the task,
even if its actions happened to satisfy the verifier.
Prompt 9 shows the initial task prompt given to the agent. Information in the template is dynamically
substituted based on the starting database state and task instruction.
