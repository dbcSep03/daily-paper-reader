# Abstract 

As teams of AI agents take on larger projects and long-standing open problems, agent collaboration offers another dimension for scaling inference-time compute. To understand what makes such collaboration effective and scalable, we develop Software World, a framework for simulating multi-agent coworking in realistic software ecosystems. It comes with a pipeline to create environments of real, interdependent Python packages of different topics, sizes, and dependency structures, which we call software worlds . In a simulation, agents maintain packages in the world with a high-level goal of improving software efficiency, and they are free to discover tasks to work on and collaborate with others. We evaluate agents’ work in a world collectively by measuring speedup in hidden dependent packages. The framework allows us to study different elements of collaboration by varying communication, ownership, and resource allocation. We run simulations in three different worlds, totaling more than 10,000 hours of agent work across eight models. Overall, performance 1Agent Collaboration at Scale via Simulated Software Worlds 

improvement scales with inference-time compute, with the best model improving downstream efficiency by up to 31%. We show that most agents can find meaningful tasks via collaboration, but some frontier models can prematurely stop looking for improvements and make little progress. We release the simulation framework and traces to support future studies of agent collaboration at https://szj.io/sw .

# 1 Introduction 

Scaling agent teams has enabled AI systems to make substantial progress on problems that are difficult and time-consuming even for human experts. For example, recent efforts have used 16 agents to build a C compiler capable of compiling Linux (Carlini, 2026), dozens to formalize Fermat’s Last Theorem (Anthropic, 2026), and approximately 10,000 working concurrently to develop a reported proof addressing the Navier– Stokes Millennium Prize problem (OpenAI, 2026). As these efforts expand from a few agents to thousands, understanding how agents work together through large-scale collaboration becomes increasingly important. To study large-scale collaboration, we introduce Software World, 1 a framework for simulating agents maintaining real repositories and robustly evaluating their collective software improvements. We construct 

software worlds from interdependent packages and instantiate agents to maintain them together. Given a broad goal to improve software efficiency, agents discover and choose tasks themselves. They are free to work with others, communicating through issues and pull requests as human developers do. The world’s collective outcome is evaluated with extrinsic signals—using tests and benchmarks from held-out dependent packages that are not visible to the agents during simulation. 

Software World leverages realistic setups for studying collaboration at scale. Human developers already organize into communities and coordinate their work across interdependent projects (Cataldo et al., 2006; Bogart et al., 2016). Unlike completing an assigned issue (Jimenez et al., 2024) or solving predefined problems (Kim et al., 2025; Pappu et al., 2026; Park et al., 2026), collaboration between maintainers results in discovering new tasks , e.g., fixing bugs reported by others, or requesting new features from dependent libraries. It creates sufficient scope for agents to divide tasks and exchange information for meaningful collaboration. Compared to studies using games and virtual worlds to study collaboration qualitatively (Park et al., 2023), Software World also provides reliable quantitative measures that reflect the practical value of agents’ collaboration outcomes. 

Software World provides configurable controls for understanding elements of collaboration. Following Bratman (1992), we consider collaboration a form of shared agency : two or more agents intentionally organize and coordinate their actions as contributions to a joint activity. Collaboration involves communication among 

task owners to coordinate their work and allocate resources toward a shared goal (Malone and Crowston, 1994). Existing studies examine these aspects in isolation, e.g., focusing on communication protocols (Park et al., 2026; Pappu et al., 2026), or configuring agent tasks and roles through specialized harnesses and fixed workflows (Fourney et al., 2024; Hong et al., 2024; Pan et al., 2025). In a software world, we can systematically control communication access, code ownership, and resource allocation to study how these conditions shape collaboration and impact the resulting work. 

We simulate software worlds with 10,000 hours of agent work. We create three representative software worlds and run simulations across eight models with 55K agent sessions totaling more than 180B tokens. Overall, we find that performance improvement scales with the compute an agent spends in its work, and collaboration helps agents discover what to work on, with the best model improving downstream efficiency by up to 31%. We see signs that break the “curse of coordination”: capable agents can meaningfully collaborate when there is clear task ownership. Surprisingly, some frontier models can stop looking for improvements and make little progress, and agents struggle to effectively allocate shared resources within the world. Our work contributes (1) Software World, a framework for simulating and evaluating collaboration among agents maintaining interdependent software packages; (2) empirical findings on how communication, ownership, and resource allocation shape agent behavior and collective performance; and (3) an open dataset of 40K agent session traces from the main experiments.

# 2 The Software World Framework 

A software world contains interdependent packages, agents that maintain them, and records of their commu-nication. Software World provides two components for studying collaboration in these worlds. SW-Env constructs the worlds and runs agents under configurable working conditions (Section 2.1). SW-Eval measures the effects of their changes on separate dependent packages (Section 2.2). 

2.1 SW-Env: The Software World Environment 

We give agents a broad goal of improving software efficiency, then let them choose what to work on and when to involve other maintainers. We construct software worlds with interdependent packages to create opportunities for collaboration, since a problem one agent discovers may require another agent to fix it. Their changes and discussions persist, so agents can build on earlier work and respond as other maintainers change the software. Below, we describe how we construct and run these worlds.  

> Constructing software worlds.

We develop a pipeline for selecting repositories from real Python packages. It identifies core packages with foundational roles in the ecosystem, such as pandas or requests , then selects 

consumer packages that use them in different ways and form different dependency structures. We manually review the resulting selections to form software worlds (see details in Appendix A). Section 3 presents worlds with different domains, sizes, and dependency structures. This pipeline could also be applied to other programming languages, although our experiments focus on Python.  

> Agents and work sessions.

In our setup, an agent is an LLM with tools and persistent memory. It is given a broad goal of improving software efficiency while preserving correctness, and we let it choose what to work on. Agents can inspect and edit code, run tests and profilers, exchange messages, and publish releases. They can also decide that no useful work remains. We extend the Harbor framework (Harbor Framework Team, 2026) to run agents over multiple sessions . Each session gives an agent a fresh sandbox with access to a Bash shell and lasts up to a configured time limit. The instructions ask agents to review their saved memory and message notifications before planning their work, then summarize what they did and update their memory and work log at the end. Code, discussions, and saved memory carry over between sessions, while the conversation starts fresh. Empirically, we find this design outperforms launching one long session per agent, as it avoids an indefinitely growing conversation and simplifies context management (Appendix C). Each agent runs one session at a time, and multiple agents can work in parallel up to a concurrency limit.  

> A shared platform for code and discussion.

We coordinate agent work through Forgejo, a software devel-opment platform similar to GitHub, where each package has its own repository. We import each package’s source code, commit history, and tags, but leave out existing issues and pull requests. All subsequent discus-sions and change proposals come from the agents. Agents discuss problems through issues and propose and review code changes through pull requests. They can continue working after sending a message without waiting for a reply. Each agent receives a unique account through which the platform enforces read/write permissions for the repositories. Within each world, we can change which repositories agents can inspect and modify, who they can commu-nicate with, and how they receive and share work-session budgets. Our later experiments vary these settings to study communication , ownership , and resource allocation (Sections 4 to 6). 

2.2 SW-Eval: Evaluating Software Worlds 

Agents’ improvements to a library in the world can benefit other software that depends on it. We use this dependency relationship to evaluate the downstream impact of agents’ work. SW-Eval evaluates whether agents’ changes make dependent software faster while preserving correctness, using human-authored benchmarks that agents never see during their work sessions.

Accounting for correctness failures. However, as agents may introduce changes that break downstream software, purely measuring performance changes may fail to capture this issue. We therefore use each held-out package’s correctness checks to determine how its tasks enter the aggregate score. Let ˜rt(k) denote the credited speedup, and TH denote the tasks from the held-out package H. If package H passes its checks at checkpoint k, each task t ∈ T H receives its measured value, ˜rt(k) = rt(k). If its checks fail, we consider two policies: 1. Strict: assign ˜rt(k) = 1 for every t ∈ T H , representing no credited improvement. 2. Carry: retain ˜rt(k) = rt(k′), where k′ < k is the most recent checkpoint at which H passed its checks. For each policy, we compute the aggregate score by replacing rt(k) with the credited speedup ˜rt(k) in the geometric mean above, yielding Sstrict and Scarry . Sstrict makes the introduction and repair of correctness failures visible in the score, while Scarry is closer to realistic software adoption, which retains the latest valid upstream release. We use carry for the main results.

# 3 Simulating Three Software Worlds 

We use Software World to construct three software worlds with different domains, sizes, and dependency structures, and we run agents from several model families in each. We first describe the worlds and the simulation setup, and then examine the resulting software improvements and the agents’ work patterns. 

3.1 Experimental Setup 

Software worlds. We create three worlds to study how agents collaborate across different types of software and dependency structures (Fig. 2). World-1 contains six networking packages built around requests and 

urllib3 , where agents optimize pure Python code. World-2 contains six data-science packages, including 

numpy and pandas , where agents can work with compiled code in addition to Python. World-3 expands to 26 packages across several dependency clusters, testing agents in a larger, more varied world. 

Models and harnesses. We run simulations with both open and closed models from five families, namely, Claude, GPT, Gemini, Kimi, and GLM. We use the Pi coding agent harness whenever possible, as we find that it reduces cost while maintaining performance (Appendix C). 4 We use the default medium reasoning level of the harness for each model, and disable subagents within sessions so that agents cannot create additional workers outside the experiment’s communication and ownership settings. For all runs, we record the token counts of each turn and estimate API costs based on the officially listed prices. 

Simulation setup. By default, each agent is assigned to maintain one repository; agent communication is allowed, and agents are encouraged (though not forced) to reach out to and discuss with others. We run each agent initially for 100 sessions and let it continue if it is still working. We stop when it decides there is nothing left to do, or when the simulation reaches 10B tokens. We track agents’ repository activity through pull requests, releases, issues, and comments. Sessions without these actions may still include local edits, tests, or updates to notes.

# 4 Communication Can Help Agents Discover Work 

The promise of communication is that one agent’s discovery can help another make progress (Park et al., 2026). A maintainer may notice that another package is slowing down its own code and share measurements with the other maintainer to help find a fix. Yet agents may exchange messages without using them effec-tively (Khatua et al., 2026). With one maintainer assigned to each of the six packages in World-1, we study whether communication helps agents discover useful work and improve downstream efficiency, and whether encouraging more communication leads to more gains.

We first compare worlds where agents can com-municate with one another ( connected ) against worlds where agents work independently ( isolated ). In connected runs, maintainers can inspect one another’s repositories and exchange feedback through issues, pull requests, and reviews. Communication is optional , so agents are free to choose whether, when, and with whom to interact. In isolated runs, repositories remain private to their maintainer.

We next test whether Sol participates when more communicative agents initiate exchanges. # 5 Clear Ownership Helps Agents Work Together 

So far, we have divided the work by assigning each agent a package to maintain. Without these assignments, agents can choose which packages to improve, but they may duplicate work or leave some packages unat-tended. Even with assigned ownership, more maintainers do not always help. With assigned packages, six Opus maintainers outperform one agent maintaining all packages (Fig. 8(a)). We examine whether this trend extends to Sol, Kimi, and Gemini, comparing one maintainer responsible for all six packages with six maintainers assigned one package each (Fig. 8(b)). For Sol and Kimi, one maintainer consistently achieves higher held-out scores than six. The Gemini results are less conclusive, with one maintainer leading at lower spending and six at higher spending. Opus’ success with six maintainers might be related to Opus also initiating the most communication among these models (Fig. 5). It is possible that its willingness to initiate exchanges helps it benefit from distributing work across maintainers. Letting agents choose their responsibilities makes dividing the work part of the task. Agents can develop their own coordination practices, but duplication and additional review can make their work more costly. Assigning packages provides a division of responsibility while preserving freedom to choose useful improvements. Whether distributing those responsibilities across agents improves performance still depends on the model.

A shared budget allows maintainers to request more resources for promising work, but requires them to judge one another’s proposals and decide which work to support. We study how Sol, Opus, and Gemini make these decisions in World-1, keeping one assigned maintainer per package.

Multi-agent collaboration. Multi-agent systems divide work through assigned roles (Hong et al., 2024; Qian et al., 2023; Huang et al., 2023), task decomposition (Chen et al., 2024a; Geng and Neubig, 2026; Anthropic,

2025), and workflows that adapt to feedback (Hu et al., 2024). Communication can improve collective search (Park et al., 2026), but agents can struggle to coordinate code changes or combine information (Khatua et al., 2026; Li et al., 2026b). The benefits of adding agents depend on the task and model (Kim et al., 2025), while studies of self-organization examine how models and protocols affect collaboration (Dochkina, 2026) and how agents learn coordination strategies that transfer to new problems (Pappu et al., 2026). Evaluations also study interaction protocols (Agashe et al., 2025; Zhu et al., 2025a), social behavior (Zhou et al., 2024), and collaboration processes and failures (Chen et al., 2026b; Cemri et al., 2025). Persistent environments also support self-organization (Chen et al., 2024b; Tessera et al., 2026) and simulated societies that evolve through agents’ actions (Park et al., 2023; Piao et al., 2025; Altera.AL et al., 2024). Shared-resource simulations examine whether agents sustain a common resource (Piatti et al., 2024), and work on agent economies proposes ways to organize exchanges and allocate resources (Tomasev et al., 2025). We study collaboration through ongoing maintenance of real software, where agents discover tasks themselves and we vary communication, ownership, and resource allocation to examine how they work together.  

> Software engineering benchmarks.

Coding benchmarks evaluate assigned issue resolution (Jimenez et al., 2024; Deng et al., 2025), work across repositories (Chen et al., 2026a), and maintenance through successive changes (Le et al., 2025; Lam et al., 2026; Chen et al., 2026c). Work on bug discovery without issue reports gives agents more responsibility for finding tasks (Li et al., 2026a; Bui and Evangelopoulos, 2026). Performance optimization benchmarks ask agents to make real software faster while preserving correctness (Shetty et al., 2025; He et al., 2025; Ma et al., 2025; Sehgal et al., 2026; Nangia et al., 2026). Our setting combines this optimization goal with task discovery and collaboration across interdependent packages. Evaluation studies also identify weak tests that accept incorrect patches, issues that reveal solutions, and other flaws in agent benchmarks (Aleithan et al., 2024; Yu et al., 2025; Wang et al., 2025; Zhu et al., 2025b). Human review and continuously updated tasks address some of these problems (OpenAI, 2024; Zhang et al., 2025). We test whether agents’ improvements benefit dependent packages using human-authored tests and benchmarks that agents cannot inspect or modify. This measures generalization beyond the work agents choose for themselves. We also use instruction counts to reduce the sensitivity to execution conditions that affects performance measurements (Chen et al., 2026d).  

> Coordination in open-source software.

Software dependencies connect maintainers’ work, so a change in one package can require changes in others (Malone and Crowston, 1994; Kikas et al., 2017; Decan et al., 2019; Venturini et al., 2023). Maintainers must negotiate who takes responsibility for these changes and the effort they require (Bogart et al., 2016, 2021). Studies link communication that follows work dependencies to faster problem resolution (Cataldo et al., 2006, 2008), and code ownership and contributor expertise to how often software defects occur (Bird et al., 2011). Brooks (1975) describes how adding developers can increase training and communication costs. These findings motivate our experiments on how agents communicate, divide responsibilities, and spend their limited resources while maintaining interdependent software. 

# 8 Conclusion 

We introduce Software World, a framework for studying collaboration among agents that choose their own work while maintaining real, interdependent software. We vary their working conditions and evaluate whether their changes improve software in dependent packages they never see. Our experiments show that agents can discover substantial improvements, yet some frontier models stop searching while useful work remains. Feedback from other maintainers can help agents find optimizations and catch bugs they miss alone. But more communication does not reliably improve performance, and additional maintainers can spend effort repeating one another’s work. Clear package responsibilities help Opus agents work together, while shared budgets reveal that agents can actively support one another yet leave resources unused. We release the framework and traces as a foundation for studying when agents benefit from working together and how to make that collaboration more effective.

# A Curating Software Worlds 

We describe how we collect candidate packages (Appendix A.1), analyze their dependencies (Appendix A.2), and select repositories for the software worlds (Appendix A.3) and held-out evaluation (Appendix A.4). Appendix A.5 lists the details of packages and held-out evaluation for the worlds used in our experiments. 

A.1 Collecting candidate packages 

Build a Candidate List. We start by building up a list of potential packages to use in our worlds. We combine two sources. The first is a set of 92 package candidates taken from prior work: Sehgal et al. (2026); He et al. (2025); Deng et al. (2025); Ma et al. (2025); Shetty et al. (2025); Nangia et al. (2026). The rest are taken from the top 15000 most popular PyPI packages in July 2026 (from https://hugovk.dev/top-pypi-packages/ ), removing stubs and nvidia CUDA packages. We keep the top 1200 remaining packages and sample 900 packages from the remaining 13.8k using stratified sampling (e.g., one package from each of the 900 equal ranges between 1200 and 15000). Finally, we query PyPI to obtain the latest stable version of each of the packages. This process leaves us with a list of 1500–2000 packages. Starting from this seed set, we use deps.dev to obtain dependencies for each of these packages and search for existing GitHub repositories that contain their source code and tests. Since we want to measure world performance, we are particularly interested in repositories that contain existing benchmarking code—we use 18 Shen et al. 

the presence of common benchmarking script files, directories, regular expressions, and tools (e.g., codspeed, pytest-benchmark, asv) to identify whether a repository contains runnable benchmarking code. For all repositories, we identify whether the declared dependencies are actually used, and for the repositories with benchmarking code, we also extract the subset of dependencies that are used in the benchmarking code directly by parsing the code into Python abstract syntax trees. The next step is to turn this set of repositories and dependencies into a dependency graph, where each node is a package and each edge indicates a dependency relationship between two packages. The edges are weighted—the edge weight is the total number of imports, references, and calls to functions from the dependency made by the consuming package. We organize the candidate pool by finding communities in this weighted graph using Louvain community detection (Blondel et al., 2008). Communities are kept only if they contain at least five packages. Based on its role in the community, each package is classified as “foundational” (if it has > 10 consumers), “intermediate” (if it has consumers and dependencies), “consumer” (if it only has dependencies), or “isolated” (if it has no consumers or dependencies). Additional metadata, such as the number of GitHub stars and topics, is also collected, and an LLM is prompted to assign a high-level domain type to each repository. 

A.2 Analyzing dependencies and code usage  

> Fine-grained Dependency graph generation.

Each repository in the candidate pool is then used for further analysis. We want to get a sense of how a dependency affects the package that consumes it. To do this, we employ two analysis techniques. The first is to use static analysis to create a more fine-grained dependency graph. We parse the package code and identify what APIs from dependencies are used and whether they are in code that is relevant to the benchmarks. However, static analysis does not provide the whole picture; it would miss that some dependencies are called multiple times (in loops) or by functions that are called from other parts of the code. To address these shortcomings, we also run dynamic analysis. We run validated benchmark harnesses in Docker containers and use sys.monitoring to record how often dependency APIs are called. The end result of this process is a more fine-grained dependency graph with information on the edges concerning which APIs are called and how often.  

> Defining code usage.

We describe how a package uses one of its dependencies in two ways. Its static usage x counts every reference to each of the dependency’s interfaces in the package’s source code. Its runtime usage y counts the calls that reach each interface when the package’s benchmark runs. The two differ because a benchmark exercises only part of a package’s code. The agent maintaining an in-world package sees all of its code, so static usage is what that agent can observe and discuss with the dependency’s maintainer. A benchmark can only register a change in a dependency through the calls it makes, so runtime usage is what an evaluation can measure. We therefore describe in-world packages by static usage and held-out packages by runtime usage. 

A.3 Choosing packages for a world  

> Selecting seed repositories.

We source repositories across diverse areas such as machine learning, web development, and data processing. We consider their roles in the dependency graph: foundational packages support many others, intermediate packages both depend on others and serve other packages, and consumer 

packages use them in applications.  

> Manually curating the final worlds.

The final step is to use this fine-grained dependency graph with its associated metadata to obtain the final worlds. We perform this curation step manually to balance the composition of the worlds and identify which packages are in the world and which are held out for evaluation.

C.4 Budget-sharing implementation limitations 

The instructions tell agents they can request shared sessions for themselves or another maintainer, but the budget system only accepts requests for the agent submitting them. Agents can still donate sessions from their own budgets to other maintainers. This mismatch prevents some approved requests from going through. For example, the system blocks a request for ten sessions for another maintainer in the default Opus run, even though three maintainers approve it. Later requests or donations provide some of these sessions, so we cannot determine how much budget this 31 Agent Collaboration at Scale via Simulated Software Worlds 

restriction leaves unused by adding up the blocked requests. In the default Sol run, agents never request sessions for another maintainer; the final two requests fail because too few maintainers still have sessions left to vote. For Opus, the unused budget may reflect both the agents’ decisions and this implementation restriction, and these runs do not establish how much each contributes.

D.1 Communication experiment case studies  

> A pool-key memo in

urllib3 (the opus-5 6 agent collaborative setup. Every request through urllib3 

goes through one function that finds the connection pool for a host. In version 2.7.29 that function rebuilt the pool key from scratch on each call: it copied two dictionaries, lower-cased the scheme and host three times, and built a thirty-field tuple, only to look up a pool that was already open under the same key. None of urllib3 ’s own benchmarks run this function, so its maintainer had no way to see the cost by profiling its own code. The isolated urllib3 maintainer, same model and same starting code, never touched it. The cost is visible from the caller’s side. The requests maintainer timed its own request path with the socket removed and found this function was the largest remaining block it did not own, about 6 of 49 microseconds per request. It opened an issue on urllib3 with the measurement, a table of what memoizing each candidate function would save, and the reason it had not cached the pool on its own side: skipping the lookup would stop refreshing the pool’s recency and let a live pool be evicted under in-flight work. Twenty-three minutes later the urllib3 maintainer opened a pull request that memoizes the derived key while keeping the lookup, and named that reason as the design constraint. It spelled out when the memo is exact and when it must be skipped, for example for any context that carries headers or socket options, since mutating those changes the key without changing the snapshot. A second consumer, requests-gssapi ,reported that its workload pays the cost twice per call, since it re-sends each request after an authentication challenge, and caught an error in the pull request’s description before release. The fix shipped in urllib3 

2.7.30 about an hour after the issue was opened. The requests maintainer then measured the release at 5 microseconds off every request, about 10%, with the same absolute saving on a real socket. The changed function is on the call path of all four held-out packages. We do not attribute a change in the held-out score to it, since another urllib3 release landed an hour later and the next sweeps moved by less than the run-to-run variation. What the case establishes is narrower: the cost could only be seen from a caller’s workload, the fix was shaped by what the caller knew about its own side, and the isolated maintainer never found it.  

> Feedback catches a bug in a Gemini optimization (single agent vs 6 agent collaboration).

In the connected Gemini run, the requests maintainer speeds up Response.content by reading the response body in one call. The package’s own 751 tests pass, but the change bypasses urllib3 ’s content-length check, allowing incomplete response bodies to pass without an error. In the isolated run, the requests maintainer makes the same change a day later and publishes 15 further releases without restoring the check. No consumer in that run tests those releases, and the held-out correctness checks do not cover this case. The comparison illustrates how testing by another maintainer can catch an error that both the package’s own tests and the held-out checks miss.
